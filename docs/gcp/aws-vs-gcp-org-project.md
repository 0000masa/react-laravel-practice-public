# GCP のアカウント / プロジェクト / 組織モデル（AWS との対比）

GCP を AWS の感覚で触ると「アカウント」「プロジェクト」「組織」の関係でつまずきやすい。
ここを AWS と対比して整理する一般リファレンス。末尾に**今回の練習環境（個人アカウント）での状況メモ**を置く。

## TL;DR

- **GCP の分離境界は「プロジェクト」**。リソース・IAM・API 有効化・請求リンク・クォータはすべてプロジェクト単位で独立する。
- 1 つの Google アカウント（ログイン）で**プロジェクトを複数持てる**。
- **おおまかな対応: AWS アカウント ≒ GCP プロジェクト**。
- **Organization は個人利用では不要**。Google Workspace / Cloud Identity（独自ドメイン）を持つと自動的に出現する。
- **請求先アカウント（Billing Account）はプロジェクトとは別物**。1 つの請求先アカウントで複数プロジェクトの支払いをまとめられる。

## GCP のリソース階層

```
Organization（任意・ドメインに紐づく最上位ノード）
 └─ Folder（任意・グルーピング）
     └─ Project（リソースの入れ物 / 分離・請求・IAM の単位）
         └─ Resource（Cloud Run, Cloud SQL, GCS, ...）

Billing Account（支払い手段を持つ別オブジェクト）──linked──> 複数の Project
```

- 上位に付けた IAM ロールや組織ポリシーは**下位に継承**される。
- Organization / Folder が無くても、Project は「組織なし（No organization）」として単独で使える。

## AWS との対応表

| AWS | GCP | 補足 |
| --- | --- | --- |
| Organization | Organization | 最上位。GCP は Workspace/Cloud Identity に紐づき自動生成 |
| OU（組織単位） | Folder（フォルダ） | グルーピング層。Organization が前提 |
| **Account（アカウント）** | **Project（プロジェクト）** | **分離・請求・IAM の主単位**。実務上の対応の中心 |
| SCP（サービスコントロールポリシー） | Organization Policy（組織ポリシー） | ガードレール。仕組みは異なる（後述） |
| 一括請求 / 支払いアカウント | Cloud Billing Account（請求先アカウント） | プロジェクトに**リンク**して使う |
| IAM（アカウントごとに独立） | IAM（階層に付与し継承） | GCP は ID を Cloud Identity に集約 |

> 注意: 「AWS アカウント ≒ GCP プロジェクト」は Google 自身の移行ガイドでも使われる標準的な対応だが、
> AWS アカウントの方が重い完全テナント境界なのに対し、GCP プロジェクトは軽量に量産できる、という質の差はある。
> 強く分離したい単位を AWS で「アカウント」、GCP で「プロジェクト（必要なら Folder で束ねる）」に割り当てる。

## プロジェクトの独立性（何が分かれるか）

1 つの Google アカウントで `app-stg` / `app-prod` のように分けると、各プロジェクトで以下が独立する。

- リソース（Cloud Run やバケットはプロジェクトに属する）
- IAM（誰が何できるかはプロジェクト単位で付与）
- **API の有効化**（プロジェクトごとにオプトイン。別プロジェクトでは再度有効化が必要）
- 請求先アカウントへのリンク（プロジェクトごとに付け替え可能）
- クォータ / 上限

→ AWS で「stg と prod を別アカウントに分けて事故を遮断する」のと同じ発想を、GCP では**別プロジェクト**で実現する。

## Organization は必須か？

| 使っている ID | Organization | 複数プロジェクト |
| --- | --- | --- |
| 個人の Google アカウント（gmail 等） | **無し**（「組織なし」配下） | **作れる**（Organization 不要） |
| Google Workspace / Cloud Identity（独自ドメイン） | **自動的に存在** | 作れる（プロジェクトは組織配下に入る） |

- Organization は「自分で有効化する機能」ではなく、**ドメイン（Workspace/Cloud Identity）に紐づいて自動生成**される。
- 個人アカウントには Organization が無いので、Folder も使えない（プロジェクトをフラットに複数持つだけ）。

## AWS Organizations と GCP Organization の違い

- **成り立ち**: AWS は「複数の独立アカウントを後から束ねる」ために**自分で作成・有効化**する層。
  GCP は **Cloud Identity / Workspace ドメインに紐づいて自動生成**される、階層の最上位ノード。
- **構成単位**: AWS は「アカウント」を作成/招待して束ねる。GCP は「アカウント」という構成単位が無く、
  **Folder / Project を階層にぶら下げる**。
- **ガバナンス**:
  - AWS **SCP** = 各アカウントで**許可できる上限**を絞る deny ガードレール。
  - GCP **Organization Policy** = **設定（構成）の制約**。例: サービスアカウントキー作成を禁止、使用可能リージョンを制限、
    外部 IP 付与を禁止など。IAM（誰が何をできるか）とは別レイヤで、組み合わせて使う。
- **ID 管理**: AWS はアカウントごとに IAM が独立し、クロスアカウントはロール信頼で繋ぐ。
  GCP は ID を Cloud Identity に集約し、IAM を組織/フォルダ/プロジェクト/リソースに付けて**継承**させる。
- **単独利用**: AWS アカウントは組織なしでも単独で完結。GCP プロジェクトも組織なしで単独利用できる。

## 請求先アカウント（Billing Account）の位置づけ

- プロジェクトとは独立したオブジェクトで、**クレジットカード等の支払い手段**を持つ。
- 1 つの請求先アカウントを**複数プロジェクトにリンク**できる（逆に、プロジェクトを別の請求先に付け替えも可能）。
- プロジェクトに請求先がリンクされていないと、有料 API / リソースの有効化で弾かれる。

| | AWS | GCP |
| --- | --- | --- |
| 支払いの単位 | AWS アカウント自体に支払い方法を紐づけ | 独立した「請求先アカウント」。1 つで複数プロジェクト分を支払える |
| プロジェクトと支払い | 概念が一体（アカウント＝請求境界） | プロジェクトを請求先アカウントに**明示的にリンク** |

## 今回の練習環境での状況メモ

- この練習では **個人の Google アカウント**を使う（会社の Workspace アカウントではない）。
  → したがって **Organization は無し**。プロジェクトは「組織なし」配下にフラットに作られ、Folder も使わない。
- 複数プロジェクト（例: 練習用とお試し用）は Organization 無しでそのまま作れる。
- **課金エラー「請求先アカウントの管理者に指定されていません」の意味**:
  個人アカウントには（会社のような）既存の請求先アカウントが無いので、**請求先アカウントをまだ作っていない**だけ。
  権限を誰かに依頼する話ではなく、**自分で請求先アカウントを 1 つ作成**して当該プロジェクトにリンクすれば解決する
  （コンソール: **お支払い → 請求先アカウントを作成 → プロジェクトをリンク**。新規利用なら無料クレジットが付く場合がある）。
- この構成の Terraform は `project_id` をプロジェクト単位で受け取る（`terraform/gcp/stg/terraform.tfvars`）。
  別プロジェクトに作り直す場合は `project_id` を差し替え、API の有効化（[manual-setup-console.md](./manual-setup-console.md) 手順2）を
  そのプロジェクトで改めて行う。
