# Docker のレイヤーと overlayfs（重ね合わせファイルシステム）

## ① 結論（先に答え）

- **レイヤー**＝イメージを構成する**読み取り専用の「差分スナップショット」**の積み重ね。Dockerfile の `FROM` / `RUN` / `COPY` / `ADD` など**ファイルシステムを変える命令ごとに1枚**できる。各レイヤーは**内容のハッシュ（digest, sha256）**で識別される。
- **overlayfs**＝それら読み取り専用レイヤーを下から重ね、一番上に1枚の**書き込み可能層**を乗せて、**1つの普通のファイルツリーに見せる**「重ね合わせ（union）ファイルシステム」。
- あなたの問い「**このディレクトリはこのレイヤー、と管理しているのか？**」への答えは **No**。レイヤーは「ディレクトリへのタグ付け」ではなく、**各レイヤーが『下の層との差分（追加/変更/削除されたファイル群）』を丸ごと持つ**もの。重ね順は **イメージ側のマニフェスト**と **ホスト側の overlay2 メタデータ**で管理されます（②で実体を見ます）。
- **なぜレイヤーに分けるのか**（一枚岩圧縮では不十分な理由）＝ **キャッシュ・再利用・重複排除**のため。ビルド高速化、push/pull の差分化、複数イメージでのベース層共有によるディスク節約——これらは「全部まとめて1つに圧縮」では全部失われます。
- **GitHub Actions → ECR**：このプロジェクトは**ビルドキャッシュを使っていないので毎回フルビルド**（あなたの見立て ⭕）。一方 **push は digest が一致するレイヤー（特にベースイメージ層）をスキップ**するので「全部アップロードよりは速い」（これも ⭕、ただしニュアンスあり）。

## ② 仕組み

### (1) レイヤーとは何か

Dockerfile の**ファイルシステムを変える命令**（`RUN` / `COPY` / `ADD`、そして `FROM` が持ち込むベース層）が、それぞれ1枚のレイヤーになります。`ENV` / `CMD` / `EXPOSE` / `WORKDIR` のようなメタ情報はファイルを変えないので、レイヤーの中身は作らず**イメージのコンフィグ（後述）に記録**されます。

各レイヤーの中身は **「直前の状態に対して、どのファイルが追加・変更・削除されたか」の差分**を tar に固めたものです。フルコピーではなく差分なのがポイント。

```
FROM php:8.2-fpm-bullseye   ← ベースイメージの複数レイヤー（OS + PHP 一式）
RUN apt-get install ...     ← レイヤー: 入れたパッケージ群の差分
COPY php.ini ...            ← レイヤー: 設定ファイル1個の差分
COPY --from=builder vendor  ← レイヤー: vendor ディレクトリの差分
COPY backend/www/ .         ← レイヤー: アプリコードの差分
```

**digest（内容アドレス）**：各レイヤーは中身を sha256 でハッシュした値で識別されます。**中身が1バイトでも違えば別の digest**。この「内容＝名前」という性質（content-addressable）が、後で出てくるキャッシュと重複排除の心臓部です。

**Dockerfile の順序 ＝ レイヤーの積み順**：Dockerfile は上から実行され、各命令のレイヤーが**下から積み上がります**。つまり **一番上の `FROM` が最下層、一番下の命令が最上層**です。

```
（最上層）COPY backend/www/ .         ← Dockerfile の一番下
  ↑       COPY --from=builder vendor
  │       COPY php.ini
  │       RUN apt-get install ...
（最下層）FROM php:8.2-fpm-bullseye    ← Dockerfile の一番上
```

この積み順が、後の (3) の「**上の層から探す**」「**後に書いた COPY が前の同じパスを上書きする**」に直結します。

### (2) 「削除」はどう表現されるか（whiteout）— レイヤーが増える理由

下の層にあるファイルを「削除」したレイヤーは、**物理的に消すのではなく「whiteout（白塗り）」という目印**を置きます（イメージの tar 内では `.wh.<ファイル名>` という特殊エントリ）。overlayfs はそれを見て「このファイルは無いことにする」と振る舞います。

つまり **削除しても下の層のファイルは残ったまま**。だからレイヤーを足すほどイメージは基本的に大きくなります。これが「`apt-get install` と `apt-get clean && rm -rf` を**同じ `RUN` にまとめる**」理由です（別レイヤーで消しても下の層に残ってサイズが減らないため）。

#### 「どのレイヤーで消しても残るなら同じでは？」← 分かれ目は「同じ RUN か別 RUN か」

ポイントは「**どのレイヤーで消すか**」ではなく、**作成と削除が "同じレイヤー" か "別レイヤー" か**です。レイヤーは「**そのコマンドが終わった時点の、差し引き（ネット）の変化**」を記録するからです。

**ケースA：同じ RUN（同じレイヤー）で作成＆削除 → 残らない**

```dockerfile
RUN truncate -s 100M /big.bin && rm /big.bin
```

RUN が終わった時点で `/big.bin` は無いので、このレイヤーの差分に **100MB は一切含まれません**。途中で作っても、差分を取る時には消えているからです。→ レイヤーはほぼ 0 バイト。

**ケースB：別々の RUN（別レイヤー）で作成＆削除 → 残る**

```dockerfile
RUN truncate -s 100M /big.bin   # レイヤーA: 「+100MB」で確定（凍結）
RUN rm /big.bin                 # レイヤーB: 「/big.bin を消した」目印(whiteout)・ほぼ0バイト
```

レイヤーA は **読み取り専用なので、後から小さく書き換えることは誰にもできません**（← (1) の「読み取り専用」がここで効きます）。レイヤーB にできるのは「無いことにする目印」を置くことだけで、**A の 100MB はイメージに同梱されたまま**。→ `docker run` した中からは `/big.bin` は見えないのに、**イメージのサイズには 100MB が乗っている**状態になります。

| 書き方 | レイヤーに入るサイズ | run 中に見える? |
| --- | --- | --- |
| 同じ RUN で作成＆削除 | **≈ 0**（最初から記録されない） | 見えない |
| 別 RUN で作成 → 別 RUN で削除 | **≈ 100MB**（A に凍結＋B に目印） | 見えない（でも容量は食う） |

だから `apt-get install` と `rm -rf /var/lib/apt/lists/*` は**同じ `RUN` にまとめる**——途中で作ったゴミを「レイヤーに焼き付ける前に」消す、というわけです。「読み取り専用（凍結）だから、後からは隠すことしかできない」が腑に落ちれば完璧です。

### (3) overlayfs（重ね合わせファイルシステム）

コンテナが「普通のファイルツリー」を見られるのは、overlayfs が複数レイヤーを重ねて1枚に合成しているからです。登場する4つのディレクトリ：

- **lowerdir**：読み取り専用。**イメージのレイヤーを複数スタック**したもの（下層）
- **upperdir**：書き込み可能な**コンテナ層**（コンテナ起動時に作られる、そのコンテナ専用の1枚）
- **merged**：合成ビュー。**コンテナの中から見える「`/`」**がこれ
- **workdir**：overlayfs が内部処理に使う作業領域

動作のルール：

- **読み取り**：上の層から順に探し、**最初に見つかった層のファイル**を返す（上の層が下を「隠す」）
- **書き込み**：**copy-on-write**。下層のファイルを書き換えるときは、まず **upperdir にコピーしてから**書く。**下層（イメージ）は決して変わらない**

```
        ┌──────────── merged（コンテナから見える / ）────────────┐
        │   上から探して最初に見つかったファイルが見える              │
        └──────────────────────────────────────────────────────┘
   upperdir   [ コンテナ書き込み層（このコンテナ専用・消すと消える） ]  ← 書き込みはここ(CoW)
   lowerdir   [ アプリコード層 ]
              [ vendor 層 ]
              [ apt パッケージ層 ]
              [ ベースイメージ層（php:8.2-fpm …）]                   ← 全部 読み取り専用・共有可能
```

**この「探す」のはいつ？** → **コンテナが動いている最中（ランタイム）に、ファイルを読むそのたび**です。イメージを解凍（pull）するときではありません。解凍時は各レイヤーを別々のディレクトリ（`overlay2/<id>/diff/`）に**置くだけ**。コンテナ起動中に overlayfs が合成ビューをマウントし、プロセスが `/etc/php.ini` を開く**たびに**「最上層から下へ探して最初に当たったものを返す」がリアルタイムに起きます。

**「上の層から」とは？** → 同じパスのファイルが複数の層にありうる、が前提です。例えば `/etc/php.ini` がベース層（下）と `COPY php.ini`（上）の両方にあるとき、overlayfs は **上＝Dockerfile で後に書いた層を先に見つけて返す**ので、あなたの `php.ini` が見え、下のデフォルトは隠れます。これが「後の COPY が前を上書きする」正体であり、whiteout（消した目印）も「上で先に目印に当たる → 無い扱い」で実現されています。((1) の「Dockerfile の順＝積み順」とつながります。)

これが姉妹編で触れた「読み取り専用レイヤー＋薄い書き込み層」の正体です。

### (4) レイヤーは「どこで」管理されているか（あなたの問いへの直接回答）

管理情報は **2階層**あります。「ディレクトリにレイヤー番号が書いてある」のではなく、**レイヤーの並び順を別の場所がリストで持っている**、というのが答えです。

#### (A) イメージ側（配布・保存の形式）＝ マニフェスト / コンフィグ JSON

イメージは「マニフェスト」と「コンフィグ」という2つの JSON を持ちます。

- **image manifest**：このイメージを構成する**レイヤーの digest と順序のリスト**（＋コンフィグへの参照）。「このイメージ＝この digest たちをこの順に重ねる」という設計図。
- **image config**：`rootfs.diff_ids`（各レイヤーの**展開後**ハッシュ）の順序リストと、`history`（**どの Dockerfile 命令で作られたか**）を持つ。

確認コマンド（読むだけ・安全）：

```bash
docker inspect <image>                 # RootFS.Layers に diff_id の並びが見える
docker history <image>                  # 各レイヤーがどの命令・何バイトか
docker manifest inspect <image>         # レイヤー digest の一覧（リモート）
```

> ここが重要：これは「**ディレクトリ → レイヤー**」の対応表ではなく、「**レイヤーをこの順で重ねよ**」という並び順リストです。各レイヤー自体が「差分の集合」で、どのファイルがどのレイヤー由来かは『重ねた結果』として決まります。

#### (B) ホスト側（pull・展開後の実体）＝ `/var/lib/docker/overlay2`

イメージを pull するとレイヤーがホストのディスクに展開されます（overlay2 ドライバの場合）：

- 各レイヤーの実ファイルは `/var/lib/docker/overlay2/<id>/diff/` に展開される（**レイヤーの実体＝この `diff/` ディレクトリ**）
- `<id>/lower`：**自分より下の層を指すポインタ**（重ね順をここで保持）
- `<id>/link`：そのレイヤーの短い識別子（パスを短くするため）

コンテナ起動時、ランタイムは
`mount -t overlay -o lowerdir=層3:層2:層1,upperdir=コンテナ層,workdir=...`
のような overlayfs マウントを組み立てます。**「どのレイヤーをどの順で重ねるか」は、この `lower` ファイル＋マウントオプションが管理**しています。

> まとめ：レイヤーの**実体はディレクトリ（`diff/`）**だが、**「このディレクトリは第N層」という重ね順の管理は別ファイル（`lower`）とマニフェスト**が担う。あなたのイメージした「管理ファイル/ディレクトリ」は、(A) マニフェスト/コンフィグ と (B) overlay2 の `lower`/`link` がそれにあたります。

### (5) なぜレイヤーに分けるのか（一枚岩圧縮との比較）

あなたの「OS・アプリ・実行環境を**全部まとめて1つに圧縮**したほうがシンプルでは？」への答え。確かにシンプルですが、レイヤーは次の実利を生みます：

1. **ビルドキャッシュ**：変わっていない命令のレイヤーは**再ビルドせず使い回す**。一枚岩だと1バイト変えただけで全再ビルド。
2. **push / pull の差分化**：レジストリ（ECR 等）は **digest 単位で blob を保存**。既にある層は再送・再取得しない。一枚岩だと毎回全部。
3. **ホストでのディスク共有**：同じベース（`php:8.2-fpm`）を使う**複数イメージがベース層を1コピーだけ共有**。一枚岩だと各イメージがフルコピーで何倍も食う。
4. **pull の並列化**：複数レイヤーを**並行ダウンロード**できる。

トレードオフ：レイヤーが増えるとメタデータや overlay の重ね処理のオーバーヘッド、whiteout でサイズが減らない、など。だから「**キャッシュが効きやすい順に命令を並べる**」「**関連処理を1 `RUN` にまとめる**」が定石になります。

> 一言でいうと：**シンプルさを少し犠牲にして、キャッシュ・再利用・重複排除という大きな実利を取っている**のがレイヤー方式です。

## ③ このプロジェクトでは

### backend Dockerfile のレイヤー設計（`docker/ecr/backend/Dockerfile`）

このイメージは**マルチステージビルド**になっています。

- **`composer-builder` ステージ**（`FROM composer:2 as composer-builder`）で依存を入れ、**最終ステージは `vendor` ディレクトリだけ `COPY --from`** で持ってくる（`Dockerfile:48`）。composer 本体やビルド中間物を最終イメージに残さない＝**イメージが小さくなる**。
- **「`composer.json` / `composer.lock` だけ先に COPY → `composer install`」**（`Dockerfile:6-8`）：依存が変わらない限り**このレイヤーはキャッシュヒット**し、`composer install` をやり直さない、というキャッシュ狙いの順序。
- **`COPY backend/www/ .`（アプリコード）は最後**（`Dockerfile:50`）：コードは頻繁に変わるので、**変わりやすいものを後ろ**に置くのがキャッシュの定石（前の層のキャッシュを守れる）。

### GitHub Actions → ECR：毎回フルビルド＋push は差分

`.github/workflows/ecr-deploy-laravel.yml:37-39` は次の2行だけです：

```bash
docker build -f ./docker/ecr/backend/Dockerfile -t $ECR_REGISTRY/...:$IMAGE_TAG .
docker push $ECR_REGISTRY/...:$IMAGE_TAG
```

- **buildx も `cache-from`/`cache-to` も GHA キャッシュも無し**、`runs-on: ubuntu-latest` の**使い捨てランナー**。
- → **ビルド**：実行ごとにローカルのレイヤーキャッシュが空なので、**毎回ゼロから全レイヤーを作り直す**（あなたの見立て ⭕）。上記 Dockerfile の「キャッシュ狙いの順序」は**1回のビルドの中**でしか効かず、ラン間では参照すべき前回レイヤーが無いため、結局**毎回 `apt-get` も `composer install` も走る**。
- → **push**：ECR はレイヤー（blob）を **digest 単位**で保存します。push 時、各レイヤーの digest が**既に ECR にあればスキップ、無ければアップロード**：
  - **ベースイメージ層**（`php:8.2-fpm-bullseye` など固定 digest）→ 一度 push 済みなら以降スキップ。**ここで「差分だけ」が効く** ⭕
  - **`RUN apt-get ...` / `install-php-extensions`** → 内容が毎回同一なら digest 一致でスキップされうるが、apt が新しいパッケージを引く・タイムスタンプ差などで **digest が変わると再アップロード**（非決定的だと効きにくい）
  - **`COPY backend/www/ .`（アプリコード）** → コミットごとに変わる＝**毎回新しい digest → 毎回アップロード**
  - `IMAGE_TAG` は `sha-<commit>` で毎回変わるが、**タグは blob へのポインタにすぎず**、重複排除は digest 基準。タグが変わっても既存 blob は再送されない

> 結論：あなたの「**push でレイヤーが効いて差分だけ＝少し速い**」は ⭕。ただし**速くなるのは push 部分（特にベース層）**で、**ビルド自体は毎回フル**、というのが正確な姿です。

### 速くする改善案（任意・提案）

> ⚠️ これは提案です。CLAUDE.md のガードレールどおり、**適用するかはご自身の判断**で。ここでは選択肢とトレードオフの提示にとどめます。

「毎回フルビルド」を縮めたいなら、**ビルドキャッシュをラン間で持ち越す**のが定石です。`docker/setup-buildx-action` ＋ `docker/build-push-action` を使い：

- **GHA キャッシュを使う**：`cache-from: type=gha` / `cache-to: type=gha,mode=max`。レイヤーキャッシュを GitHub Actions Cache に保存・復元 → 変わっていない層（`apt`・`composer install`）をスキップしてビルド短縮。`mode=max` はマルチステージの中間ステージもキャッシュ対象。
- **レジストリ（ECR）をキャッシュ置き場にする**：`cache-to: type=registry,ref=<ecr>/...:buildcache` / `cache-from: type=registry,...`。

トレードオフ：

- GHA キャッシュは**容量上限**（リポジトリあたり約 10GB・LRU で古いものが追い出される）。大きいイメージだと追い出されてヒット率が落ちる。
- レジストリキャッシュは **ECR のストレージ/転送が増える**。
- **非決定的ビルド**（apt が latest を引く等）はキャッシュヒット率が落ちる → パッケージのバージョン固定で改善。
- そもそも「毎回フルでも許容できる所要時間」なら、**ワークフローを複雑化しない**判断も十分アリ。

## ④ 落とし穴・よくある誤解

- **レイヤーは「足すと増える」**：`rm` でファイルを消しても**下層に残る**（whiteout）。サイズ削減には「同じ `RUN` 内で生成＆削除」か「マルチステージで成果物だけ持ってくる」（このプロジェクトの `COPY --from=composer-builder vendor` がまさにそれ）。
- **キャッシュは「変わったら以降全部無効」**：Dockerfile のある行が変わると、**その行以降のレイヤーは全部キャッシュ無効**。だから変わりにくいもの（依存インストール）を上、変わりやすいもの（アプリコード）を下に置く。
- **digest は内容ハッシュ**：同じ Dockerfile でも、ベースイメージが更新されたり apt が別バージョンを引くと**digest が変わり、キャッシュも重複排除も外れる**。
- **タグ ≠ イメージ実体**：タグは digest へのポインタ。同じ digest に複数タグも付けられる。push の重複排除はあくまで **digest 基準**。
- **overlayfs の書き込みは copy-on-write**：コンテナ内で**巨大ファイルを書き換える**と upperdir にフルコピーされて遅く・容量も食う。永続データは外（ボリューム）へ（→ 姉妹編 container-memory-vs-ssd.md）。

## 用語集

- **レイヤー** — イメージを構成する読み取り専用の差分スナップショット。Dockerfile の FS を変える命令ごとに1枚
- **digest** — レイヤー（やイメージ）の中身を sha256 でハッシュした内容アドレス。中身が違えば別 digest。キャッシュ・重複排除の鍵
- **diff_id** — レイヤーの**展開後**の中身のハッシュ（イメージコンフィグに順序付きで並ぶ）
- **blob** — レジストリが保存する圧縮済みレイヤーの実体。digest で識別・重複排除される
- **マニフェスト / イメージコンフィグ** — イメージを構成するレイヤーの digest と順序、作成履歴を記した JSON
- **overlayfs** — 複数の読み取り専用レイヤー＋書き込み層を1つのファイルツリーに合成する union ファイルシステム
- **lowerdir / upperdir / merged / workdir** — 順に、読み取り専用の下層スタック / 書き込み可能なコンテナ層 / 合成ビュー / 作業領域
- **copy-on-write（CoW）** — 下層のファイルを変更するとき、上層にコピーしてから書く方式。下層は不変
- **whiteout** — 下層のファイルを「削除扱い」にする目印。物理削除ではないのでサイズは減らない
- **マルチステージビルド** — 複数の `FROM` を使い、ビルド用ステージの成果物だけを最終イメージに COPY する手法
- **ビルドキャッシュ** — 変わっていない命令のレイヤーを再利用する仕組み。`buildx` の `cache-from`/`cache-to` でラン間にも持ち越せる
- **buildx** — BuildKit ベースの拡張ビルダ。外部キャッシュ・マルチプラットフォーム等に対応
