# フロントエンドの仕組み 〜ブラウザは結局なにを理解できるのか〜

## この記事の結論（最重要）

> **ブラウザが直接理解できるのは HTML・CSS・JavaScript の3つだけ。**
> JSX・TypeScript・SCSS・Tailwind の記法などは、そのままでは動かない。
> だから Vite などの **ビルドツール** が「素の3言語」へ翻訳してからブラウザに渡している。

- **ライブラリなしの素のページ** → `.html` / `.css` / `.js` を置くだけで動く。`package.json` も `node_modules` も Vite も**不要**。
- **React / Tailwind / SCSS を使う** → ブラウザが読めないので、ビルドで素の HTML/CSS/JS に**変換が必要**。

---

## 1. ブラウザは「3つの言語」しか読めない

ブラウザは、3種類の食材しか調理できない料理人のようなもの。

| 言語 | 役割 | たとえ |
|---|---|---|
| **HTML** | 構造・中身 | 家の骨組み |
| **CSS** | 見た目 | 壁紙・塗装 |
| **JavaScript** | 動き | 電気・水道などの動く設備 |

React の JSX、TypeScript、SCSS、Tailwind の `class="bg-blue-500"` は、
**すべて「翻訳してから」でないとブラウザは理解できない。** これが全ての出発点。

---

## 2. ライブラリなしの素のWebページ

`<head>` の中で、読み込む CSS と JS を指定する。

```html
<!DOCTYPE html>
<html>
<head>
  <link rel="stylesheet" href="style.css">   <!-- 外部CSSを読み込む -->
  <style> p { color: red; } </style>           <!-- CSSを直接書いてもOK -->
  <script src="main.js" defer></script>       <!-- 外部JSを読み込む -->
</head>
<body>
  <p>こんにちは</p>
  <script>
    console.log("scriptタグの中に直接書いたJSも動く"); <!-- インラインJS -->
  </script>
</body>
</html>
```

- **CSS** … 外部ファイル（`<link>`）でも `<style>` 内に直接書いてもよい。
- **JS** … 外部ファイル（`<script src>`）でも `<script>` 内に直接書いてもよい。
- `<link>`/`<script src>`（外部）と `<style>`/`<script>`（直接記述）は**役割は同じで、置き場所が違うだけ**。
- ブラウザに渡るのは**最初から素の3言語**なので、**翻訳（ビルド）は不要**。
- よって `package.json` も `node_modules` も**いらない**。ファイルをダブルクリックで開けば動く。

---

## 3. ブラウザがページを読み込む流れ

ブラウザは「HTML を最初に取得し、その中で参照されている部品を後から取りに行く」。

1. ブラウザが `index.html` を取得する。
2. 上から**パース（解析）**しながら、`<link href="style.css">` や `<script src="main.js">` を見つける。
3. 見つけるたびに「それも下さい」と**追加のリクエスト**をサーバーに送って取得する。

```
ブラウザ →「index.html ください」 → サーバー
ブラウザ ← index.html を受け取る
   ↓ HTMLを解析中に <link> や <script> を発見
ブラウザ →「style.css も main.js もください」 → サーバー
ブラウザ ← それぞれ受け取って適用・実行
```

つまり **HTML は最初の設計図**で、それを読んだブラウザが必要な部品を芋づる式に取りに行く。

> **重要：CSS / JS は HTML の中で参照して初めて適用される。**
> 同じフォルダに `style.css` や `main.js` を置いただけでは、ブラウザは勝手に読み込まない。
> HTML に `<link rel="stylesheet" href="style.css">` や `<script src="main.js">` と
> **明示的に書いて初めて**、ブラウザがそれを取りに行く。HTML は「設計図」であると同時に「目次（指示書）」でもある。
>
> ```
> docs/
> ├── index.html   ← この中に <link>/<script> の記述が無ければ…
> ├── style.css    ← 置いてあるだけ。誰も読まない
> └── main.js      ← 置いてあるだけ。誰も実行しない
> ```
>
> - パスを間違えてもエラーで止まらず「スタイルが当たらないだけ」になりがち。開発者ツールの Network タブで 404 を確認するとよい。
> - 逆に HTML が正しく指していれば、別フォルダや別サーバー（CDN）の CSS/JS でも読み込める。条件は「同じフォルダにあるか」ではなく「**HTML が正しく指す先にあるか**」。

### 補足：フォルダにアクセスしたとき返すファイルは設定で変えられる

「フォルダごとに index.html が返る」のは**Webサーバーの慣習（デフォルト値）**であり、設定で変更できる。

```nginx
# nginx の例
index main.html index.html;   # main.html を優先、なければ index.html
```
```apache
# Apache の例
DirectoryIndex main.html
```

- `https://example.com/blog/` のように**ファイル名を省略**すると、サーバーが設定に従ってデフォルトのファイルを返す。
- ローカルで `file://` で直接開くときは、自分で `about.html` のように名前を指定して開く（index.html という名前は必須ではない）。

## 4. React / Tailwind / SCSS を使う場合（ビルドが必要）

ここで `package.json` / `node_modules` / Vite が登場する。

```
あなたが書くコード                Vite（ビルドツール）          ブラウザに渡るもの
─────────────────                ──────────────────          ──────────────────
App.tsx   (JSX + TS)     ──┐
Button.tsx               ──┤                                index.html
styles.scss (SCSS)       ──┼──▶  変換・まとめる・圧縮   ──▶  assets/index-abc123.js
Tailwind の class        ──┤    （トランスパイル + バンドル）  assets/index-def456.css
node_modules 内の React 本体 ─┘
```

### 登場人物

- **package.json** … 「この計画に必要な部品リスト」。どのライブラリを使うかを書く。
- **node_modules** … `npm install` で実体がダウンロードされてくる、部品の置き場。
- **Vite** … ビルドツール。下の2つの仕事をする。

### ビルド（`npm run build`）でやっていること

1. **トランスパイル（翻訳）**：JSX / TypeScript / SCSS → 素の JS / CSS へ変換。
2. **バンドル（束ね）**：何十個ものファイルを少数にまとめ、圧縮する。

→ 結果は `dist/`（出力フォルダ）に、
   **`index.html` ＋ `index-xxxx.js` ＋ `index-xxxx.css`** のような**素の3言語**として出力される。
   これをサーバーに置けば、ブラウザはライブラリの存在を知らないまま動かせる。

> **「最終的に Vite で index.html / js / css に変換される？」→ はい、その通り。**

## 5. 動的にHTMLを作る昔ながらの方式（PHP など）

ここまでは「最初から完成した HTML がサーバーに置いてある（＝静的サイト）」話。
一方、**アクセスのたびにサーバーが HTML を組み立てる**方式もある。

Webサーバーに「`.php` にアクセスが来たら、ただ返すのではなく **PHP に渡して実行**してね」と設定しておくと：

```
ブラウザ →「/page.php ください」
   ↓
Webサーバー →「.php だから PHP に実行させよう」
   ↓
PHP が処理：DBからデータ取得 → HTMLを組み立てる
   ↓
Webサーバー → 出来上がった「素のHTML」をブラウザに返す
```

- **重要：ブラウザは PHP を一切知らない。** サーバー側で PHP が HTML を作り終えてから渡すので、
  ブラウザに届くのは結局「素の HTML」。
- これを **サーバーサイドレンダリング（SSR）** と呼ぶ。
- 静的サイト（完成済みHTMLを返すだけ）との違いは、**アクセスのたびに中身を動的に組み立てる**点。

## 6. 「SSR」と「MPA」は別の軸（混乱しやすい用語の整理）

「昔ながらの PHP サイトは SSR？ MPA？」——答えは**どちらも正しい**。
両者は反対語ではなく、**測っている軸が違う**だけ。

| 軸 | 問い | 対になる言葉 |
|---|---|---|
| **どこで HTML を作るか** | サーバー？ ブラウザ？ | **SSR ↔ CSR** |
| **ページ構成のしかた** | 複数のHTML？ 1枚で切り替え？ | **MPA ↔ SPA** |

> 「SSR の反対は MPA」ではない。**SSR の反対は CSR、MPA の反対は SPA。**

### 軸A：どこで HTML を作るか（SSR ↔ CSR）

- **SSR（Server-Side Rendering）**：HTML を**サーバー側**で組み立てて完成品を渡す。
- **CSR（Client-Side Rendering）**：ほぼ空の HTML を渡し、**ブラウザ側**の JS が中身を組み立てる（React の典型）。

### 軸B：ページ構成のしかた（MPA ↔ SPA）

- **MPA（Multi-Page Application）**：ページごとに別々の HTML があり、リンクで**ページ全体を読み込み直す**。
- **SPA（Single-Page Application）**：HTML は実質1枚で、JS が中身を差し替えて画面を切り替える（ページ全体の再読み込みなし）。

### 組み合わせで見る（2軸なので4通り）

```
                MPA（ページ全体を読み直す）   SPA（1枚で切り替え）
SSR（サーバーで作る）   昔ながらのPHPサイト ★      Next.js のSSR
CSR（ブラウザで作る）   （まれ）                  素のReact (Vite) ★
```

- **昔ながらの PHP サイト** = 「サーバーで作る（SSR）」かつ「ページごとに別HTML（MPA）」。**両方の性質を持つ**。
- だから「MPAでは？」も「SSRでは？」も、見ている軸が違うだけでどちらも正しい。
- **よくある混乱**：「SSR ↔ SPA」「CSR ↔ MPA」と対比させてしまうこと。軸が違うので対にならない。
- Next.js などは境界を曖昧にし、**SSR なのに SPA**（初期HTMLはサーバーで作り、その後はJSで切り替え）も可能。
  「PHP=SSR、React=CSR」と単純化しすぎないのがコツ。

## 7. つまずきポイント

- **`npm run dev` と `npm run build` は別物。**
  - `dev`：開発中。Vite が裏でリアルタイム翻訳しながらサーバーを立てる（保存で即反映）。
  - `build`：本番用。`dist/` に最終成果物を吐き出す。**ユーザーに届くのは build の成果物。**
- **ファイル名の `index-abc123.js` のハッシュ**はキャッシュ対策（キャッシュバスティング）。
  中身が変わるとファイル名が変わるので、ブラウザが古いキャッシュを使い続ける事故を防ぐ。
  - 流れ：①`index.html` は基本キャッシュさせず毎回取得 → ②中の JS 名がハッシュで変わる → ③名前が違うので新しい JS を取りに行く。
- **「React＝必ずビルド」ではない**（CDN 読み込みの裏技もある）が、
  TS/JSX/SCSS/多数ファイルのバンドルが必要なので、実務ではほぼ必ずビルドする。

## 用語集

- **ビルド** — 開発用のコードを、本番でブラウザが読める形に変換・最適化する工程。
- **トランスパイル** — ある言語を別の言語へ翻訳すること（例：TypeScript → JavaScript）。
- **バンドル** — 複数ファイルを1つ（少数）にまとめること。
- **パース** — テキストを解析して意味を取り出すこと。ブラウザは HTML を上から順にパースする。
- **node_modules** — ダウンロードした外部ライブラリの実体が入るフォルダ。
- **package.json** — プロジェクトが使う部品（依存ライブラリ）の一覧を書く設定ファイル。
- **CDN** — ライブラリをネット経由で直接読み込む配信網。ビルドなしで React を使う裏技に使える。
- **キャッシュ** — 一度読んだファイルをブラウザが保存して再利用する仕組み。
- **キャッシュバスティング** — ファイル名を変えることで、古いキャッシュを使わせず最新を取得させる手法。
- **サーバーサイドレンダリング（SSR）** — アクセスのたびにサーバー側で HTML を組み立てて返す方式。
- **クライアントサイドレンダリング（CSR）** — ほぼ空のHTMLを返し、ブラウザのJSが中身を組み立てる方式。
- **MPA（マルチページアプリ）** — ページごとに別HTMLがあり、遷移で全体を読み直す構成。
- **SPA（シングルページアプリ）** — HTMLは実質1枚で、JSが中身を差し替えて画面を切り替える構成。
- **静的サイト** — 完成済みの HTML ファイルをそのまま返す方式。
