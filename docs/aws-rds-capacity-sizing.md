## 0. 全体像：容量選定は「型番選び」ではなく「メトリクス駆動の調整」

容量選定の本質は、最初に完璧なスペックを当てることではなく、**小さく始めてメトリクスを見ながら正しい方向に動かす**ことです。動かす軸は 2 つだけ：

- **垂直（スケールアップ/ダウン）**: インスタンスクラスを上げ下げする（または ACU の Max を上げる）。**書き込みボトルネックの基本対処**。
- **水平（スケールアウト/イン）**: 読み取りレプリカ/リーダーを増減する。**読み取りボトルネックの基本対処**（→ 構成の選定は options-reference.md）。

```mermaid
flowchart TD
    M[メトリクスを観測] --> CPU{CPU 使用率が高い?}
    CPU -->|常時 70%超| UP1[垂直: クラスを上げる<br/>or コンピュート最適化系へ]
    CPU -->|スパイク的| BURST[バースト型 t を検討<br/>or 上位クラス]
    M --> MEM{メモリ不足?<br/>FreeableMemory 低 / スワップ}
    MEM -->|Yes| UP2[垂直: メモリ最適化 r 系へ<br/>or サイズを上げる]
    M --> IO{ディスク読み書きが<br/>ボトルネック?<br/>高い ReadIOPS / 処理待ち}
    IO -->|Yes| OPT[Optimized Reads 系（NVMe）<br/>or IOPS/スループット引き上げ]
    M --> READ{読み取り負荷が重い?}
    READ -->|Yes| OUT[水平: レプリカ/リーダー追加<br/>→ 構成の見直し]
```

> **鉄則**: 本番でいきなり大きいクラスを張らない。**観測 → 1 段ずつ調整**。RDS/Aurora はインスタンスクラスの変更が（再起動を伴うが）容易なので、過剰プロビジョニングはコストの無駄になりやすい。Serverless v2 はこの調整自体を自動化したもの（§5.4）。

## 1. インスタンスクラスの読み方（命名規則）

`db.r6g.large` のような型番は、**意味のある区切り**でできています。読めると選定が一気に楽になります。

```
db . r 6 g d . large
│    │ │ │ │   └─ サイズ（large, xlarge, 2xlarge … 数字が大きいほど vCPU/メモリが倍々）
│    │ │ │ └───── サフィックス（追加機能を表す文字。下表参照。無いことも多い）
│    │ │ └─────── プロセッサ（g = AWS Graviton, i = Intel, a = AMD, 無印 = Intel旧世代）
│    │ └───────── 世代（数字が大きいほど新しい：5→6→7→8→9）
│    └─────────── ファミリー（t=バースト, m=汎用, r/x/z=メモリ最適化, c=コンピュート最適化）
└──────────────── DB インスタンスであることを示す接頭辞
```

**サフィックス（末尾の小文字）の意味** — `db.x2iedn` のように複数つくこともあります：

| 文字 | 意味 | ざっくり言うと |
|---|---|---|
| `d` | ローカル **NVMe SSD** 内蔵（[用語集](#用語集): NVMe / Optimized Reads） | インスタンスに直結した超高速ディスクが付く。読み取りや一時処理が速い |
| `n` | **ネットワーク帯域**を強化 | 通信速度（Gbps）が太い。大量データの送受信に強い |
| `e` | **メモリ拡張**（extra memory） | 同じクラスより搭載メモリが多い |

例（`db.x2iedn` = メモリ最適化 X 系・第2世代・Intel・メモリ拡張・NVMe 付き・ネット強化）：
- `db.t4g.medium` … バースト型・第4世代・Graviton2・medium サイズ
- `db.r6g.large` … メモリ最適化・第6世代・Graviton2・large サイズ
- `db.m8i.2xlarge` … 汎用・第8世代・Intel・2xlarge サイズ
- `db.r6gd.xlarge` … メモリ最適化・第6世代・Graviton2・**ローカル NVMe 付き**（[Optimized Reads](#用語集)）・xlarge
- `db.m6idn.large` … 汎用・第6世代・Intel・NVMe 付き・ネット強化・large

> **サイズの感覚**: 1 段上げる（例 `large`→`xlarge`）ごとに **vCPU とメモリがおおむね 2 倍**、料金もおおむね 2 倍。`large` が基準サイズで、その下に `medium` / `small` /（バースト型のみ）`micro` があります。

## 2. インスタンスファミリーの特徴

RDS のインスタンスクラスは用途別に 5 系統あります。**「CPU・メモリ・I/O のどれが効くか」でファミリーを選ぶ**のが基本です。

RDB は「[OLTP](#用語集)（オンラインの細かい読み書き。注文・ログイン・在庫更新など、Web/業務アプリの典型）」を扱うことが多く、その性質に合わせてファミリーを選びます。

| ファミリー | 記号 | 特徴 | 向いている DB ワークロード |
|---|---|---|---|
| **バースト** | `t`（t4g/t3/t2） | 普段は低い CPU（ベースライン＝契約上の最低保証分）で動き、必要なときだけ一時的に CPU を全開にできる（＝**バースト**）。安い。RDS では Unlimited モード＝ベースラインを超えた分は追加課金で継続的に全開を維持できる | 開発・検証、たまにしか動かない・低負荷、小規模本番。**ずっと CPU が高い用途には不向き**（バースト用の貯金＝クレジットを使い切ると遅くなる/追加課金が増える） |
| **汎用** | `m`（m9g/m8g/m7i…） | CPU・メモリ・ネットワークが**バランス型**（メモリ:vCPU ≒ 4GiB:1コア） | クセのない一般的な[OLTP](#用語集)、Web アプリのバックエンド。最初の本番の定番 |
| **メモリ最適化** | `r` / `x` / `z` | **vCPU あたりのメモリが多い**系統。`r` 系は 8GiB:1コア。`x` 系はさらにメモリが多く**最大数 TiB（テラバイト級）**まで載る（巨大データをメモリに載せたい用途）。`z` 系は**動作周波数（クロック）が高い**＝1 コアあたりの処理が速い（[用語集: クロック](#用語集)。メモリ量ではなく CPU の速さの話） | 大きな[バッファプール](#用語集)（データのメモリキャッシュ）が効く DB、結合・集計が重い、メモリ常駐量が多い。**RDB の本番でよく効く** |
| **コンピュート最適化** | `c`（c6gd） | vCPU あたりの CPU 性能比が高い。**RDS では `db.c6gd` のみ**で、しかも**Multi-AZ DB クラスター専用**（通常の単一/Multi-AZ インスタンスでは選べない）。`medium` サイズを持つ唯一のクラスター用クラス | CPU がボトルネックで、かつクラスター構成、というニッチ |
| **Optimized Reads** | `d` サフィックス（r6gd / r6id / m8gd / r8gd 等） | [Optimized Reads](#用語集)＝**ローカル NVMe SSD（インスタンス直結の超高速ディスク）** を使い、一時テーブルやソートのあふれ（メモリに収まらず一時的にディスクへ書く処理）を高速ローカルディスクで捌く → 読み取り/複雑クエリが速い | 大きな一時テーブルを使うクエリ、複雑な分析的読み取りが多い[OLTP](#用語集) |

> **DB は基本「メモリ最適化（r 系）」が効きやすい**: RDB は[バッファプール](#用語集)（よく使うデータをメモリにためておく仕組み）が大きいほどディスクへの読み書き（I/O）が減って速くなるため、汎用 `m` で性能が頭打ちならまず `r` 系を検討します。逆に開発・低負荷ならバースト `t` 系でコストを抑えるのが定石。なお **Aurora は `m`（汎用）や `c`（コンピュート最適化）を提供せず、`r` 系（メモリ最適化）/ `t` 系（バースト）/ `db.serverless` が選択肢**です。

## 3. 世代（ジェネレーション）の特徴

型番の数字（`6g` の `6`）が**世代**です。**原則として新しい世代ほど価格性能比が良く、同じ料金でより多くの vCPU・メモリ・EBS/ネットワーク帯域**が得られます。プロセッサ別に整理します。

| プロセッサ | 記号 | RDS の世代例 | 特徴 |
|---|---|---|---|
| **AWS Graviton** | `g` | Graviton2=`6g`/`x2g`/`t4g`、Graviton3=`7g`、Graviton4=`8g`、Graviton5=`9g` | Arm ベースの自社設計チップ。**同等の Intel/AMD より価格性能比が高く、コスト効率が良い**。MySQL/PostgreSQL/MariaDB はほぼ Graviton で問題なく動く。**迷ったら Graviton（`g` 付き）が第一候補** |
| **Intel** | `i`（または旧世代の無印） | `m8i`/`m7i`/`m6i`、`r7i`/`r6i`、`z1d`、`x2i` 系 | [x86](#用語集)（昔から PC/サーバーで使われる CPU 方式）。[SAP](#用語集) 認定など**特定の企業向けソフトの動作保証要件**や、x86 でしか動かないソフト・拡張命令が要る場合に。[高クロック](#用語集)（z1d）や超大メモリ（x2i：最大 4TiB）はこちら |
| **AMD** | `a` | （RDS では限定的） | [x86](#用語集) 互換。Intel より安いことがある |

> **実務の指針**:
> - **まず Graviton 系（`g`）を選ぶ** — 価格性能比が最良で、マネージド RDB ではアプリ非互換の心配がほぼない（DB エンジンは AWS が Arm 対応済み）。
> - **最新世代を選ぶ** — 旧世代（`m4`/`m3`/`t2` 等）は提供終了プロセスに入っているものが多い。新規は最新〜1 つ前の世代から選ぶ。
> - **Intel を選ぶのは要件があるときだけ** — [SAP](#用語集) 認定、超大メモリ（x2i）、特定の[高クロック](#用語集)など。

## 4. サイズの選び方（共通の判断手順）

ファミリー・世代を決めたら、最後に**サイズ**（vCPU/メモリ量）を決めます。**「最初の見積もり → 観測 → 調整」**が全構成共通の流れです。

### ステップ 1：初期サイズの当て方

- **既存 DB からの移行**: 現行の vCPU/メモリ/ピーク接続数/IOPS を基準に、同等〜やや上のサイズから。
- **新規**: まず小さめ（開発=`t` 系、本番=`m`/`r` 系の `large` あたり）から始め、負荷試験で確かめる。**過剰プロビジョニングは後で下げる手間より、最初に小さく始めて上げる方が安全**。

### ステップ 2：観測すべき主要メトリクス（CloudWatch / Performance Insights）

| メトリクス | 何を表す値か | 高い/不足のときの対処 |
|---|---|---|
| **CPUUtilization** | CPU がどれだけ使われているか（%）。100% に近いほど CPU が限界 | 垂直アップ。一時的なスパイクなら `t` 系、常時高いなら上位クラス/コンピュート寄り |
| **FreeableMemory** | 空きメモリ量（バイト）。少ないほどメモリ逼迫 | メモリ最適化 `r` 系へ、またはサイズアップ。[バッファプール](#用語集)不足はクエリ遅延に直結 |
| **SwapUsage** | メモリが足りずディスクを代用（スワップ）した量。0 が理想で、増えると遅い | 同上（メモリを増やす） |
| **ReadIOPS / WriteIOPS** | 1 秒あたりのディスク読み取り/書き込み**回数**（[IOPS](#用語集)） | ストレージの IOPS/[スループット](#用語集)を引き上げる、または [Optimized Reads](#用語集)（NVMe）系へ |
| **DiskQueueDepth** | ディスク処理待ちの行列の長さ。長い＝ディスクが追いついていない | 同上（ストレージ性能 or Optimized Reads） |
| **DatabaseConnections** | 現在の同時接続数。上限（`max_connections`、メモリ量で決まる）に張り付くと新規接続が弾かれる | サイズアップ、または **RDS Proxy**（接続をまとめて使い回す仕組み）導入 |
| **ReplicaLag**（レプリカ） | レプリカが本体からどれだけ遅れているか（秒）。大きいと「古いデータを読む」状態 | レプリカのサイズを本体に合わせる/増設 |

> ここでの「**ボトルネック**」とは、システム全体の速度を頭打ちにしている一番の制約のこと（一番細い所が全体の流量を決める）。「CPU がボトルネック」なら CPU を、「ディスク I/O がボトルネック」ならストレージを強化する、という具合に**詰まっている所を見つけて手当てする**のが容量調整です。

### ステップ 3：垂直（性能アップ）か水平（台数追加）か

- **書き込み・CPU・メモリがボトルネック** → 垂直（クラス/サイズアップ）
- **読み取りがボトルネック** → 水平（レプリカ/リーダー追加 → 構成の見直し）

## 5. 構成別の選び方

### 5.1 RDS 単一 / Multi-AZ インスタンス

**選ぶもの**: インスタンスクラス（ファミリー × 世代 × サイズ）。Multi-AZ インスタンスでもスタンバイは**プライマリと同じクラス**になります（個別指定不可）。

| 観点 | 指針 |
|---|---|
| **ファミリー** | 開発/検証・低負荷 → **`t` 系（バースト）**。一般本番 → **`m`（汎用）**。メモリが効く/`m`で頭打ち → **`r`（メモリ最適化）**。一時テーブル多用の読み取り → **Optimized Reads（`r6gd` 等）** |
| **世代/プロセッサ** | **Graviton（`t4g`/`m7g`/`r7g`/`r8g` 等）を第一候補**。Intel が要るのは SAP・超大メモリ等の要件があるときだけ |
| **サイズ** | `large` を起点に、§4 のメトリクスで上下。Multi-AZ は同一クラスが 2 台分課金になる点を織り込む |
| **注意** | `t` 系は常時高 CPU だとバーストクレジット枯渇 + Unlimited 課金で割高になりうる。本番の常時負荷には `m`/`r` を選ぶ |

**推奨スタート例（目安）**: 開発 `db.t4g.medium` / 小規模本番 `db.m7g.large`（or `db.r7g.large`） / メモリ重め本番 `db.r7g.xlarge`。

### 5.2 RDS Multi-AZ DB クラスター

**選ぶもの**: インスタンスクラス。ただし**対応クラスが NVMe ローカルストレージ（`d` サフィックス）系に限定**されます（公式の対応リスト）：`db.c6gd`, `db.m5d`, `db.m6gd`, `db.m6id`, `db.m6idn`, `db.m8gd`, `db.r5d`, `db.r6gd`, `db.r6id`, `db.r6idn`, `db.r8gd`, `db.x2iedn`。1 ライター + 2 リーダーが**全て同じクラス**になります。

| 観点 | 指針 |
|---|---|
| **ファミリー** | 汎用 → `m6gd`/`m8gd`、メモリ最適化 → `r6gd`/`r8gd`、CPU 寄り → `c6gd`（唯一 `medium` サイズあり＝小さく始めたいクラスター向き） |
| **世代/プロセッサ** | Graviton 系（`m6gd`/`r6gd`/`r8gd`/`c6gd`）が価格性能比で有利。Intel は `m6id`/`r6id`/`x2iedn` 等 |
| **サイズ** | `c6gd.medium` 以外は基本 `large` 以上。3 インスタンス分の課金になるためサイズ影響が大きい |
| **注意** | 通常の単一/Multi-AZ インスタンスとは**選べるクラス集合が違う**（`d` 無しの素の `m7g`/`r7g` などは不可）。設計時に対応表を必ず確認 |

**推奨スタート例（目安）**: 小さく始める → `db.c6gd.medium`、一般 → `db.m6gd.large`、メモリ重め → `db.r6gd.large` / `db.r8gd.large`。

### 5.3 Aurora プロビジョンド

**選ぶもの**: インスタンスクラス。**Aurora は `m`（汎用）も `c`（コンピュート最適化）も提供せず**、選択肢は **`r` 系（メモリ最適化）/ `t` 系（バースト）/ `db.serverless`（→ 5.4）** です。ライターとリーダーで**別々のクラス**を指定できます（リーダーを小さくしてコスト調整、なども可）。

| 観点 | 指針 |
|---|---|
| **ファミリー** | 開発/低負荷 → **`t` 系（`db.t4g.medium` 等）**。本番は基本 **`r` 系（メモリ最適化）一択**（Aurora に汎用 `m` は無い） |
| **世代/プロセッサ** | **Graviton を第一候補**：`db.r8g`（Graviton4）/ `db.r7g`（Graviton3）/ `db.r6g`（Graviton2）。Intel は `db.r7i`/`db.r6i`。低コスト大メモリは `db.x2g`（Graviton2） |
| **Optimized Reads** | 一時テーブル/スピルが多い読み取りには `db.r6gd`/`db.r6id`/`db.r8gd`（※ `r6gd`/`r6id` は **Aurora PostgreSQL のみ**対応） |
| **ライター/リーダーの非対称** | リーダーは読み取り専用なので、用途次第でライターより小さいクラスでコストを抑える選択も可。ただしフェイルオーバー先になるリーダーはライター相当を推奨 |
| **サイズ** | `db.r7g.large` を起点に §4 のメトリクスで調整。読み取りが足りなければ**サイズアップより先にリーダー追加（水平）**が定石 |

**推奨スタート例（目安）**: 開発 `db.t4g.medium` / 本番 `db.r7g.large`（ライター・リーダー各1）/ メモリ重め `db.r8g.xlarge` or `db.x2g.large`。

### 5.4 Aurora Serverless v2（ACU レンジ）

**選ぶもの**: 固定クラスではなく **ACU（Aurora Capacity Unit）の `Min`〜`Max` レンジ**。**1 ACU ≒ 約 2 GiB メモリ + 相応の vCPU/ネットワーク**。設定したレンジ内で Aurora が**秒単位に容量を自動増減**します。

| パラメータ | 取りうる値 | 決め方 |
|---|---|---|
| **MinCapacity** | **0 ACU**（オートポーズ対応バージョン）または **0.5 ACU**、以降 0.5 刻み | アイドル時のコスト下限。**0** にすると一定アイドル後に自動停止（コストほぼゼロ、ただし復帰に時間）。本番で常時即応が要るなら `0.5`〜必要メモリ分を確保。Min は「アイドル時もキャッシュを温存したい量」で決める |
| **MaxCapacity** | **最大 256 ACU**、0.5 刻み | ピーク時に許す上限。**コストの上限ガード**でもある。ピーク負荷想定（CPU/メモリ）から逆算。高すぎると暴走時に高額化、低すぎるとピークで頭打ち |
| **SecondsUntilAutoPause** | 300〜86,400 秒（Min=0 のときのみ有効） | 自動停止までのアイドル時間 |

**決め方のコツ**:
- **Min**: 「常時保持したいバッファプール量 ÷ 2GiB」が目安。開発なら `0`〜`0.5`、本番なら平常時の負荷をさばける下限（例 `2`〜`8`）。
- **Max**: 「ピーク時に同等プロビジョンドなら選ぶクラスのメモリ ÷ 2GiB」。例：ピークが `db.r7g.4xlarge`（128GiB）相当なら ~64 ACU。
- **注意**: 常時高負荷で張り付くワークロードは ACU 単価がやや割高なため、**固定プロビジョンド（5.3）の方が安い**ことがある。Serverless v2 は「変動が大きい/読めない/アイドルが長い」ときに効く。

**推奨スタート例（目安）**: 開発 `Min 0 / Max 4`、変動の大きい本番 `Min 2 / Max 32`、まず様子見 `Min 0.5 / Max 16`。

### 5.5 Aurora Limitless（ACU）

**選ぶもの**: シャードグループの**最大 ACU**。これを指定すると[ルーターとシャード](#用語集)の初期数が決まり、各ノードはその範囲内で自動スケールします（Aurora **PostgreSQL のみ**）。書き込みを水平分割できる唯一の構成。

> **シャードとルーターとは**（[用語集](#用語集)も参照）: **シャード**＝データを複数に分割した「保管庫」。例えば `users` テーブルを 3 シャードに分けるなら、`id` などの**シャードキー**を一定の規則（多くは `hash(id) を 3 で割った余り`）で振り分け、**各シャードが全レコードの約 1/3 ずつを保持**します（1 件ずつではなく、まとまり単位）。各シャードが自分の担当分の書き込みを並行処理する → 全体の書き込み能力が台数分に増える。**ルーター**＝アプリから来たクエリを「どのシャードに行くべきか」判断して振り分ける受付係。アプリはルーターにだけ接続すればよい。
>
> **シャード数を後から変えにくいのはこのため**: 3→4 シャードに増やすと「3 で割った余り」が「4 で割った余り」に変わり、**ほぼ全レコードの配置先がズレるため、大量データを別シャードへ物理的に移動（リバランス）**する必要があります。データが大きいほど重く時間がかかります。

| 作成時の最大 ACU | 初期ルーター数 | 初期シャード数 |
|---|---|---|
| 16〜400 ACU | 2 | 2 |
| （中間帯は段階的に増加） | … | … |
| 2301〜6144 ACU | 8 | 16 |

**決め方のコツ**:
- **最大 ACU は「想定する書き込みの処理量の合計」から決める**。Limitless の存在意義は書き込みの水平分割なので、「ピーク時に全シャード合計でどれだけ書き込むか」を基準に最大 ACU を見積もる、という意味です。上の表のとおり**最大 ACU が大きいほど初期シャード/ルーター数も多くなる**＝処理能力の総量が決まります。
- **シャード/ルーター数は後から大きく変えにくい**。理由は、シャード数を変えると**既に分散済みの大量データを別シャードへ再配置（リバランス）**する必要があり、これが重く時間のかかる処理だからです（SQL でシャード分割やルーター追加自体は可能だが運用負荷が大きい）。だから**最初の最大 ACU 設定が重要**。
- **コンピュート冗長（compute redundancy）を有効にすると、各シャードに予備のコピーが付くためシャード総数が 2〜3 倍に増えます**（その分コストも増える）。これは[HA（高可用性）](#用語集)＝あるシャードが障害で落ちても予備が即座に引き継いで止まらないようにするため。「冗長＝予備を持つ」ので、予備の数だけシャードが増える、という関係です。
- **大原則**: Limitless は**最後の手段**。まず Aurora の垂直強化（5.3 で `r` 系を上げる）+ 読み取りはリーダーで水平、で足りないか必ず先に検討する。単一ライターの書き込み上限が本当にボトルネックのときだけ。

### 5.6 Aurora Global Database（クラス と ACU）

**選ぶもの**: グローバル DB は「プライマリ + 最大10セカンダリリージョン」の集合で、**各リージョンのクラスターごとに 5.3 / 5.4 と同じ要領で②を選びます**（プロビジョンドのクラス、または `db.serverless` の ACU レンジ）。リージョンごとに独立に決められます。

| 役割 | 容量の決め方 |
|---|---|
| **プライマリ（書き込み）** | 全リージョンの書き込みを一手に引き受けるので、**書き込み負荷に十分なサイズ**。5.3（`r` 系）または 5.4（ACU レンジ）で、ピーク書き込みを基準に |
| **セカンダリ（読み取り）** | そのリージョンの**読み取り負荷に合わせて独立に**サイズ/ACU を決める。読み取りが軽い [DR](#用語集)（災害復旧。普段は使わず、障害時の備えとして置く）専用リージョンなら小さめ、現地ユーザーが多いリージョンは大きめ/リーダー増設。Serverless v2 にすればリージョン別の変動に自動追従できコスト効率が良い |
| **混在** | プライマリはプロビジョンド固定、セカンダリは Serverless v2、といった**リージョンごとに型を変える**構成も可能 |

**決め方のコツ**:
- プライマリは「自リージョンの書き込み + [ライトフォワーディング](#用語集)で他リージョンから転送されてくる書き込み」の合計を基準にサイズを決める。
  - **ライトフォワーディングとは**: セカンダリは本来読み取り専用ですが、この機能を有効にすると、セカンダリに来た書き込みリクエストを Aurora が**自動でプライマリへ転送**して処理してくれます（アプリ側で「書き込みは別リージョンのプライマリへ」という振り分けを作らなくて済む）。その結果、書き込みは結局すべてプライマリに集まるため、プライマリのサイズ見積もりに含めます。
- **昇格先は事前に固定されているわけではありません**。リージョン障害時のフェイルオーバー（災害時・データ損失の可能性あり）や計画的なスイッチオーバー（無停止・データ損失なし）を実行する際に、**「どのセカンダリをプライマリに昇格させるか」をその時に指定**します（API では昇格対象のクラスターを指定する）。
  - したがって運用上は、**いざ昇格させたいセカンダリ（少なくとも 1 つ）を、昇格後に全書き込みを捌けるサイズにしておく**必要があります。読み取り用に小さくしたセカンダリしか無いと、昇格後に書き込みで詰まります。
- 各セカンダリは現地の読み取り需要に合わせて個別最適化。変動が読めないリージョンは Serverless v2 が有利。

## 用語集

本文に出てくる用語を、初めて触れる人向けに噛み砕いて説明します。

| 用語 | 説明 |
|---|---|
| **OLTP**（Online Transaction Processing） | オンラインで発生する**細かい読み書きを大量にさばく処理**のこと。注文登録、ログイン、在庫の増減、いいね、など Web/業務アプリの典型的な DB アクセス。対義語は OLAP（大量データを集計する分析処理＝Redshift などが得意） |
| **IOPS**（Input/Output Operations Per Second） | ストレージ（ディスク）が **1 秒あたりに処理できる読み書きの回数**。「細かいアクセスを何回さばけるか」の指標。多いほど速い |
| **スループット** | ストレージやネットワークが **1 秒あたりに転送できるデータ量**（MB/s など）。「太いホースで一気に流せる量」。IOPS が"回数"なのに対し、スループットは"量" |
| **ボトルネック** | システム全体の速度を頭打ちにしている一番の制約。一番細い所が全体の流量を決める。容量調整は「どこが詰まっているか」を見つけて手当てすること |
| **バッファプール** | DB が**よく使うデータをメモリ上にためておく仕組み**（キャッシュ）。ここにデータがあればディスクを読まずに済むので速い。メモリが大きいほどバッファプールも大きくでき、性能が上がる |
| **NVMe SSD** | インスタンスに**直結された非常に高速な SSD**。ネットワーク越しのストレージ（EBS）より低遅延。型番の `d` サフィックスが付くと内蔵される |
| **Optimized Reads** | 上記の NVMe SSD を活用する RDS/Aurora の機能。メモリに収まりきらない一時データ（巨大なソートや結合の途中結果＝「あふれ／スピル」）を高速な NVMe に逃がすことで、重い読み取り・複雑クエリを速くする |
| **クロック（動作周波数）** | CPU が 1 秒間に刻む処理サイクル数（GHz）。**高いほど 1 コアあたりの処理が速い**。メモリ量とは無関係で「CPU の速さ」の話。`z1d` などが高クロック |
| **x86** | Intel/AMD が長年使ってきた CPU の命令方式（PC やサーバーで主流）。一方 Graviton は Arm という別方式。**x86 でしか動かないソフトや拡張命令**がある場合は Intel/AMD（x86）を選ぶ必要がある |
| **SAP** | ドイツ SAP 社の大企業向け業務システム（会計・在庫・人事などをまとめた ERP）。SAP **アプリ本体とその裏側のデータを保存する DB がセット**で動く（DB は SAP のバックエンド）。SAP 社は「この構成なら正式サポート」という動作保証リスト（「**SAP 認定**」）を公開しており、その中に DB を動かすインスタンスの型番条件がある。そのため **SAP システムのバックエンド DB を AWS で動かす場合は、SAP 認定済みの Intel 系インスタンスを選ぶ必要があることがある**（例：`db.m7i`）。「特定の業務ソフトがサーバー構成を指定してくる」ケースの代表例 |
| **HA**（High Availability＝高可用性） | 障害が起きても**サービスを止めない／すぐ復旧できる**ようにする設計。予備（冗長）を持たせ、壊れたら自動で引き継ぐのが基本。例：Multi-AZ、Limitless のコンピュート冗長 |
| **DR**（Disaster Recovery＝災害復旧） | リージョン全体が落ちるような**大規模障害に備える**仕組み。別リージョンにデータの複製を置き、いざという時そちらへ切り替える。HA が「日常の障害対策」なら DR は「広域災害対策」 |
| **シャード** | データを複数に分割した「保管庫」。例えば顧客データを ID で複数に分けて別々のシャードに保存し、各シャードが担当分の書き込みを並行処理する → 全体の書き込み能力が台数分に増える（＝水平分割）。Aurora Limitless で使われる |
| **ルーター** | シャード構成で、アプリのクエリを「どのシャードに行くべきか」判断して振り分ける受付係。アプリはルーターにだけ接続すればよい |
| **ライトフォワーディング** | Aurora Global Database の機能。本来読み取り専用のセカンダリリージョンに来た**書き込みを自動でプライマリへ転送**して処理する。アプリ側でリージョン別の書き込み振り分けを作らずに済む |
| **フェイルオーバー / スイッチオーバー** | プライマリが使えなくなった時などに、別のインスタンス/リージョンを新しいプライマリに**昇格**させる切り替え。**フェイルオーバー**＝障害時の切り替え（データ損失の可能性あり）、**スイッチオーバー**＝計画的な無停止切り替え（データ損失なし） |
