# コンテナはメモリで動くのか、SSD で動くのか

## ① 結論（先に答え）

「プログラムが動く」とは、結局すべて **CPU + メモリ（RAM）上で実行される** ことです。これはコンテナでもそうでなくても変わりません。SSD（ストレージ）は「動く場所」ではなく「**置き場所**」です。

- **実行中のコード・プロセス** → 必ず **メモリ（RAM）上** で動く
- **コンテナイメージ・ファイル本体** → ふだんは **SSD（ディスク）上** に置いてある
- コンテナを起動すると、SSD 上のファイルが必要に応じてメモリに読み込まれ、CPU が実行する

つまり「コンテナはメモリで動くの? SSD で動くの?」という問いは、半分は言葉の切り分けの問題です。**「実行=メモリ」「保管=SSD」** と分けて考えるのがコツです。

そして大事な点：**コンテナは「軽量な仮想マシン」ではなく、ただのプロセス（OS から見れば普通のプログラム）です。** だから「コンテナ専用の動き方」をするわけではなく、PC で普通にアプリを動かすのと根っこは同じです。

---

## ② なぜ / 仕組み

### そもそも「プログラムが動く」とは

PC でアプリを動かすとき、中ではこう動いています。

1. アプリのファイル（実行ファイル）は **SSD に保存**されている
2. 起動すると、OS がそのファイルを **メモリ（RAM）に読み込む**
3. **CPU がメモリ上の命令を1つずつ実行**する
4. 計算途中の値や変数も、すべて **メモリ上**に置かれる

ポイントは **「CPU はメモリしか直接触れない」** ことです。SSD は CPU から見ると遠い倉庫で、CPU は SSD の中身を直接実行できません。必ず一度メモリに運んでから実行します。

> 🏠 **比喩**：SSD は「**倉庫**」、メモリは「**作業机**」、CPU は「**作業する人**」。
> 倉庫（SSD）にしまってある道具は、机（メモリ）に出してこないと使えません。人（CPU）は机の上のものしか触れません。机は速いけど狭い（容量が小さい）、倉庫は遅いけど広い（容量が大きい）。

これはコンテナを使おうが使うまいが、ゲームでもブラウザでも全部同じです。

### コンテナとは何か（仮想マシンとの違い）

「コンテナ」という名前から、独立した小さなパソコンを丸ごと作っているイメージを持ちがちですが、実態は違います。

- **仮想マシン（VM）**：OS をまるごともう1つ動かす。重い。
- **コンテナ**：**ホスト（土台の）OS のカーネルをそのまま借りて、プロセスを「隔離」しただけ**。中身はただのプロセス。

Linux には「**名前空間（namespace）**」と「**cgroups**」という仕組みがあります。

- **namespace**：そのプロセスから見える「世界」を区切る。コンテナの中からは、自分専用のファイルシステム・プロセス一覧・ネットワークしか見えない。「隣のコンテナや、ホスト本体が見えない」ようにする目隠し。
- **cgroups**：そのプロセスが使える CPU やメモリの量に上限をかける。

> 🏢 **比喩**：コンテナは「**仮想マシンという別の建物**」ではなく、「**同じオフィスの中をパーティション（仕切り）で区切った個室**」。電気も空調（＝OS カーネル）は建物全体で共有しているが、各個室の中からは隣の個室が見えない。

だから「コンテナの中で動いているコード」も、結局はホスト OS の上で動く **普通のプロセス = メモリで実行されている** ことに変わりはありません。

### コンテナイメージ（SSD 側）と 実行中のコンテナ（メモリ側）

ここを分けて理解すると一気にクリアになります。

| 用語 | 何か | どこにある |
| --- | --- | --- |
| **イメージ (image)** | コンテナの「設計図・ひな型」。アプリ本体＋ライブラリ＋OS のファイル一式を固めた読み取り専用のパッケージ | **SSD（ディスク）** |
| **コンテナ (container)** | イメージを起動して動き出した「実行中の実体」（プロセス） | 実行は **メモリ**、書き込んだファイルは一時領域（後述） |

`docker compose up` でやっていることは、

1. イメージ（SSD 上のひな型）を用意する（`build` で作るか、`image:` で取ってくる）
2. それを元にプロセスを起動する → ここで初めて **メモリを使って動き出す**

```
[SSD]  イメージ（ひな型・読み取り専用）
   │  docker run / docker compose up
   ▼
[メモリ] コンテナ（実行中のプロセス）＝ CPU が実行している
```

### コンテナが書き込んだデータはどこへ？

コンテナの中でファイルを作ったり書き換えたりすると、それは「**書き込み可能レイヤー**」という一時領域に書かれます。これは基本 **ホストの SSD 上**にありますが、**コンテナを消すと一緒に消える**のが原則です。

消えてほしくないデータ（DB の中身など）のために **ボリューム（volume）** や **バインドマウント** を使います。これは「コンテナの外（ホストの SSD）にデータを逃がす」仕組みです。後半でこのプロジェクトの例を見ます。

## ③ このプロジェクトでは

### docker-compose.yml の2種類の「外部ディスクとの接続」

`docker-compose.yml` を見ると、`volumes:` に2つの書き方が混ざっています。これがご質問の「バインドマウント」の核心です。

**(A) バインドマウント** … `ホストのパス:コンテナのパス` の形

```yaml
# laravel コンテナ (docker-compose.yml:29-32)
volumes:
  - "./backend:/var/www/php"                       # ← ホストの ./backend を直結
  - "./logs:/var/www/logs"
  - "./environment/laravel/.env:/var/www/php/www/.env"
```

```yaml
# react コンテナ (docker-compose.yml:112-113)
volumes:
  - "./frontend:/var/www/html"                     # ← ホストの ./frontend を直結
```

**(B) 名前付きボリューム** … Docker が管理する保存領域

```yaml
# mysql コンテナ (docker-compose.yml:79-81)
volumes:
  - "mysql_data:/var/lib/mysql"                     # ← Docker 管理の領域に DB を保存

# ファイル末尾で宣言 (docker-compose.yml:139-145)
volumes:
  mysql_data:
    driver: local
```

### ご質問への直接回答：「バインドマウントしたコードはメモリで動いている？」

> Laravel / React コンテナのバインドマウントで、コンテナ内にあるコードはメモリで動いている？

**整理するとこうです：**

1. **コードの「ファイル本体」** … あなたの PC（ホスト）の `./backend` や `./frontend` という **SSD 上の実フォルダ** にあります。`docker-compose.yml:30` と `:113` でそれをコンテナ内のパスに「**マウント（接続）**」しています。バインドマウントは**コピーではなく、ホストのフォルダをコンテナから覗いている（直結している）**だけです。だから VSCode でホスト側のファイルを編集すると、コンテナ内のファイルも即座に変わります（＝ホットリロードが効く理由）。

2. **実行中のプロセス** … `php-fpm`（`docker-compose.yml:40`）や `npm run dev`（`:120`）が動き出すと、その PHP / Node のプロセスは **メモリ上で実行**されます。PHP がコードを読むときは、SSD 上のファイルを読み込んでメモリ上で解釈・実行します。

**つまり：コードという「ファイル」は SSD（ホストの実フォルダ）にあり、それを読んで実行する「プロセス」はメモリで動いている。** バインドマウントは「ファイルの置き場所をホスト SSD にしている」だけで、実行がメモリで起きること自体は何も変わりません。

> 🔌 **比喩**：バインドマウントは「**USB メモリを挿す**」のに似ています。USB（ホストの SSD フォルダ）を PC（コンテナ）に挿すと、PC からその中のファイルが見える。でもファイルを「実行」するときは、いつも通り PC のメモリに読み込んで動かす。USB に挿したまま編集すれば中身は即反映される。

なぜこのプロジェクトが開発環境でバインドマウントを使うのか？ → **コードを書き換えるたびにイメージを作り直さなくていい**からです。ホスト側でファイルを編集 → コンテナ内のプロセスがその新しいファイルを読む、という流れで開発が速く回ります。

## ③-2 補足：PHPコードは「いつ」メモリに載るのか（php-fpm と OPcache）

「バインドマウントしたコードはメモリで動く」と分かったうえで、さらに踏み込んだ疑問 ——
**コンテナ起動時に全コードがメモリに読み込まれるのか？ それともリクエストが来た瞬間に読むのか？** を整理します。

ここでは「**リクエストを待ち受けるプロセス**」と「**アプリのPHPコード**」を分けて考えるのが鍵です。

### (A) リクエストを待ち受けるプロセス（php-fpm）= 起動時に常駐

`docker-compose.yml:40` の `php-fpm` は、**コンテナ起動時にメモリに常駐**します。「マスター + ワーカー」というプロセスプールで、起動後はずっとメモリに居座り、リクエストを待ちます。

> 🏪 **比喩**：php-fpm は「開店中のレジ係たち」。客（リクエスト）が来る前から立っていて、来たら対応する。客が来てから雇うのではない。

### (B) アプリのPHPコード = リクエストごとに必要なぶんだけ読む（素の挙動）

PHP はインタプリタ言語で、Laravel は **オートロード**（クラスを使う瞬間に対応ファイルを読む仕組み）を使います。なので素の挙動は：

1. リクエストが来る
2. そのリクエストに必要なクラス／ファイルだけを **SSD から読む**
3. PHP が **opcode（中間コード）にコンパイル**
4. メモリ上で実行
5. リクエスト終了で、その実行に使ったメモリ（変数等）は解放される

つまり **起動時に全コードがメモリに載るのではなく、リクエストごとに必要なぶんを読んで実行**しています。

### (C) OPcache が「毎回SSDから読む」を消す

毎リクエストで「SSD読込→コンパイル」は無駄なので、**OPcache** が入ります（`environment/ecr/php.ini:48-74`、コメントが丁寧なので一読推奨）。OPcache は **コンパイル済み opcode をメモリ（共有メモリ）に保持**します。

```
[1回目]   SSD読込 → コンパイル → メモリにキャッシュ → 実行
[2回目〜] （メモリのキャッシュを直接実行）← SSDに触らない
```

さらに本番設定 `opcache.validate_timestamps = 0`（`php.ini:74`）は「**ファイル更新のチェックすらしない**」。本番イメージは不変なので、毎回の `stat()` も無駄、という判断です。**一度キャッシュに載れば、そのコードについて二度とディスクを見に行きません。**

### (D) もう1段：OS のページキャッシュ

仮に OPcache が無くても、Linux は一度読んだファイルを **ページキャッシュ**としてメモリに保持します。2回目以降の「ファイル読込」は物理 SSD ではなく RAM 上のキャッシュから返ります。OS レベルでも「よく使うものはメモリに置く」が働いています。

### まとめ：3つのモデルの正誤

| モデル | 正誤 |
| --- | --- |
| コンテナ起動時に全コードをSSD→メモリに読み込む | ❌ アプリコードは起動時には載らない（php-fpm プロセスは載る） |
| リクエストが来た時にSSDから取り出して実行 | ⭕ PHPの素の挙動はこれ（必要なファイルだけ遅延読込） |
| 常駐プロセスがリクエストに応じてコードを読み込み実行 | ⭕⭕ 一番正確。+ 2回目以降は OPcache でSSDすら触らない |

### 開発と本番で設定が正反対になる理由

「コードのファイルがどこの SSD にあるか（バインドマウントか焼き込みか）」は、この実行モデルを変えません。どちらも「php-fpm 常駐 → リクエストごとに必要コードを読む → OPcache がメモリにキャッシュ」です。変わるのは設定の意図です（`php.ini:73` のコメント参照）。

- **本番**：`validate_timestamps = 0` → コードは変わらない前提。一度キャッシュしたら二度とディスクを見ない（最速）。コードを変えたいときは**新しいイメージで入れ替える＝デプロイし直す**。
- **開発**：これを `1` にする（か OPcache を弱める）必要がある。さもないと、**バインドマウントでファイルを編集しても OPcache が古い opcode を握り続け、変更が反映されない**。

> 💡 このプロジェクトのローカル用 `docker/laravel/Dockerfile` は、この本番用 `php.ini` を **COPY していません**。だからローカルは PHP デフォルト挙動で動き、編集が反映されます。`environment/ecr/php.ini` は本番（ECR）イメージ用の設定です。これが「開発はホットリロード、本番は焼き込み＋OPcacheで固定」という正反対チューニングの正体です。

## ④ ECS（Fargate / EC2）ではどうなるか

「クラウドで動かすと根本的に変わるのか?」が気になるところだと思います。**結論：動く原理（メモリで実行・SSD に保管）は一切変わりません。** 変わるのは「**誰が土台のサーバー（ホスト）を用意・管理するか**」です。

### 普通の PC（ローカル）の場合

- **ホスト** = あなたの PC
- あなたの PC の CPU・メモリ・SSD を使ってコンテナが動く
- Docker Engine もあなたが入れて管理する

### ECS on EC2 の場合

- **ホスト** = あなたが立てた **EC2 インスタンス（＝クラウド上の仮想サーバー）**
- その EC2 の CPU・メモリ・ディスク（EBS）を使ってコンテナが動く
- **EC2 という「サーバー」の存在をあなたが意識・管理する**（台数、スペック、OS のパッチ当てなど）
- ローカルとの違いは「PC がクラウドの仮想サーバーに変わっただけ」。動き方は同じ。

### ECS on Fargate の場合（このプロジェクトの本番構成）

- **ホスト** = AWS が裏で用意する、**あなたからは見えないサーバー**
- あなたは「**CPU をいくつ、メモリを何 GB**」とだけ指定する（タスク定義）。サーバーそのものは管理しない＝**サーバーレス**
- AWS が裏で適切なサーバーを見つけ、そこにコンテナを配置して動かす
- それでも結局、AWS のどこかの物理サーバーの **メモリ上でプロセスが実行され**、イメージはディスクから読み込まれている。**原理は同じ**

> 🚗 **比喩**：
> - **ローカル PC** = 自分の車を自分で運転（全部自前）
> - **EC2** = レンタカー（車＝サーバーは借り物だが、運転・給油・管理は自分）
> - **Fargate** = タクシー（行き先＝CPU/メモリ要件だけ伝える。車の手配・整備は運転手＝AWS 任せ）
>
> どれも「エンジン（CPU/メモリ）で走る」原理は同じ。違うのは「車を誰が管理するか」だけ。

### 本番（ECS）とローカルの決定的な違い：バインドマウントは使わない

ここが実務上とても重要です。

- **ローカル開発**：コードを **バインドマウント**（ホストのフォルダ直結）して、編集を即反映させる
- **本番（ECS）**：コードは **イメージの中に焼き込む（ビルド時に COPY する）**。バインドマウントは使わない

なぜ違うのか？

- 本番には「あなたの PC のフォルダ」が存在しません。Fargate のホストは AWS が用意する使い捨てのサーバーで、そこにあなたのソースコードのフォルダは無い。だから**コードはイメージの中に同梱して持っていく**必要があります。
- 本番は「速い書き換え」より「**どこで動かしても同じ状態が再現できる**」ことが大事。イメージに焼き込めば、イメージさえあれば毎回まったく同じ環境が立ち上がります（再現性・不変性）。

```
[ローカル開発]                    [本番 ECS/Fargate]
ホスト(自PC)のフォルダ              イメージの中にコードを焼き込み
   │ バインドマウント                  │ ビルド時に COPY 済み
   ▼ 編集が即反映                      ▼ イメージ単位で配布・起動
コンテナ                           コンテナ（ホストのフォルダに依存しない）
```

> 💡 だから「ローカルで動いたのに本番で動かない」が起きやすいポイントの1つが、ここ（マウント前提か、焼き込み前提か）です。

## 落とし穴・よくある誤解

- **誤解1：「コンテナ=軽い仮想マシン」** → 違います。VM は OS ごと、コンテナはプロセスを隔離しただけ。だからコンテナは起動が速く軽い。
- **誤解2：「コンテナを消してもデータは残る」** → 残りません。書き込みは一時領域に行くので、消えてほしくないものは volume / バインドマウントで外に逃がす（このプロジェクトの `mysql_data` がまさにそれ）。
- **誤解3：「Fargate はサーバーが無い」** → 「サーバーを**管理しなくていい**」だけで、物理的なサーバーは裏で存在します。メモリで動くのは同じ。
- **メモリは有限**：`cgroups` でコンテナに割り当てたメモリを超えると、プロセスが強制終了（OOM Kill）されます。Fargate でメモリ指定が小さすぎると本番でアプリが落ちる、というのはこの仕組みのため。

## 用語集

- **メモリ（RAM）** — CPU が直接読み書きする高速な作業領域。電源を切ると消える（揮発性）。「実行はここで起きる」
- **SSD / ディスク** — 電源を切っても消えない保存領域（不揮発性）。「ファイルの保管場所」
- **イメージ (image)** — コンテナのひな型。アプリ＋依存＋OS ファイルを固めた読み取り専用パッケージ。SSD 上にある
- **コンテナ (container)** — イメージを起動した実行中の実体。中身はただのプロセス
- **プロセス** — OS が実行しているプログラムの単位。メモリ上で動く
- **namespace（名前空間）** — コンテナから見える世界（ファイル・プロセス・ネットワーク）を区切る Linux の隔離機能
- **cgroups** — コンテナが使える CPU・メモリ量に上限をかける Linux の機能
- **バインドマウント** — ホストの実フォルダをコンテナ内のパスに直結する仕組み。コピーではなく直結なので編集が即反映
- **ボリューム (volume)** — Docker が管理する永続データ保存領域。コンテナを消しても残る
- **ホスト** — コンテナが動く土台。ローカルなら自PC、EC2 ならその仮想サーバー、Fargate なら AWS が用意するサーバー
- **OOM Kill** — メモリ上限超過でプロセスが強制終了されること
- **サーバーレス** — サーバーの存在はあるが、その管理を自分でしなくてよい運用モデル（Fargate など）
- **php-fpm** — PHP の常駐プロセス管理（FastCGI Process Manager）。起動時にメモリ常駐し、リクエストを待ち受けるワーカープールを持つ
- **オートロード** — クラスを使う瞬間に対応ファイルを読み込む Laravel/Composer の仕組み。コードが遅延読込される理由
- **opcode** — PHP ソースをコンパイルした中間コード。CPU が扱いやすい形
- **OPcache** — コンパイル済み opcode をメモリにキャッシュし、再コンパイルとディスク読込を省く拡張
- **validate_timestamps** — OPcache がファイル更新を毎回チェックするか。本番0（チェックしない＝最速）、開発1（変更を反映）
- **ページキャッシュ** — OS が一度読んだファイルをメモリに保持する仕組み。2回目以降の読込が速い
