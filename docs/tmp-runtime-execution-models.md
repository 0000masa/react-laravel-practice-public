# 実行モデル比較：php-fpm / Node常駐サーバー / Lambda / Cloudflare Workers

## ① 結論（先に答え）

「コードは SSD に保管され、実行はメモリで起きる」という大原則（姉妹編で説明）は**4つすべてで共通**です。違うのは **「リクエストをどうさばくか」「プロセスがいつ生まれて、いつ死ぬか」** です。ここが4者を分ける本質です。

ざっくり一言でいうと：

- **php-fpm**：リクエストごとにワーカーが1件を担当。**毎回まっさらな状態**から始める（共有なし）。
- **Node常駐サーバー**：**たった1つのプロセス**が、イベントループで**大量のリクエストを同時並行**にさばく。状態はメモリに残り続ける。
- **AWS Lambda**：リクエスト（イベント）が来た**瞬間に環境（micro-VM）が起動**。使い終わるとしばらく再利用され、やがて捨てられる。**コールドスタート**がある。
- **Cloudflare Workers**：そもそも**コンテナでも VM でもない**。**V8 isolate** という超軽量な箱で動き、**コールドスタートがほぼ 0**。代わりにファイルシステムが無く制約も多い。

## ② それぞれの仕組み（8つの軸で見る）

以下、8つの軸で1つずつ見ていきます。

> 軸：①実行の単位 / ②常駐しているか / ③コードはいつメモリに載るか / ④コールドスタート / ⑤リクエスト間で状態が残るか / ⑥ファイルシステム / ⑦並行リクエストのさばき方 / ⑧どこで動くか / ⑨メモリ増減（アイドル↔負荷）

各セクションの末尾に、特に重要な **「コードのライフサイクル」3点（📥どのコードがいつメモリに展開されるか／⚡何がいつ実行されるか／📊メモリの増減）** をまとめてあります。ここを4方式で見比べると違いが立体的になります。前提として、メモリは2種類に分けて考えます —— **「コードのメモリ」（プログラム本体。展開タイミングが方式ごとに違い、基本は一定）** と **「データのメモリ」（リクエストごとに確保されるオブジェクト等。負荷で増減する）**。

### (1) php-fpm（おさらい＋並行性の補足）

- **①実行の単位**：OS プロセス（マスター＋複数ワーカー）
- **②常駐**：する。起動時からワーカーがメモリに居座る
- **③コードのロード**：リクエストごとに必要ファイルを遅延読込 →（OPcache 有効なら）2回目以降はメモリの opcode を再利用
- **④コールドスタート**：実質意識しない（常駐しているので）
- **⑤状態の残存**：**残らない（shared-nothing）**。各リクエストはまっさらなメモリから始まり、終了で破棄
- **⑥ファイルシステム**：あり（コンテナ／ホストのディスク）
- **⑦並行性**：**プロセス（ワーカー）を複数並べる**。1ワーカー＝同時に1リクエスト。10件同時なら最低10ワーカー必要
- **⑧どこで**：自前PC / EC2 / Fargate などのコンテナ内

> 🏪 **比喩**：レジ（ワーカー）を何台も並べた店。1台のレジは一度に1人しか対応できない。混んだらレジを増やす。各客の対応は独立していて、前の客の情報は次に持ち越さない。

PHP が「shared-nothing（毎回まっさら）」なのは弱点に見えて、**状態の取り違えが起きにくい**という安全性の利点でもあります。

**コードのライフサイクル（php-fpm｜本プロジェクトの本番設定）**

- 📥 **メモリ展開**：ワーカーは**起動時に10個固定**（`pm = static`、`zz-custom.conf:7,12`）でメモリ常駐。アプリのコードは**初回実行時に OPcache（共有メモリ）へ載り**、以降は全ワーカーで共有（読み取り専用）。なお**コードの実体は、ECR から取得したイメージを解凍してディスク（Fargate のエフェメラルストレージ）に展開したもの**で、そこから OPcache 用にメモリへ読み込む（詳細 → ③-3）
- ⚡ **実行**：リクエストのたびに空きワーカー1つが担当。そのワーカーがリクエスト用データを `memory_limit = 256M` 以内で確保 → 終了で解放（shared-nothing）。`pm.max_requests = 1000` で1000件ごとにワーカーを再起動（リーク対策）
- 📊 **メモリプロファイル**：ベースライン（10ワーカー＋共有 OPcache）は**一定**。その上に**データ部分が「同時処理リクエスト数 × 各リクエストの使用量（最大256M）」で乗り降り**する

### (2) Node.js 常駐サーバー（Express / Next.js SSR など）

ここが php-fpm と最も鋭く対照的です。

- **①実行の単位**：**1つのプロセス**（基本シングルスレッド）
- **②常駐**：する。`node server.js` で起動したプロセスがずっと生きている
- **③コードのロード**：**起動時に `require`/`import` で必要モジュールを一括で読み込み・解析**し、メモリに常駐させる。以降リクエストのたびに読み直さない（V8 が頻出コードを JIT で機械語化して更に高速化）
- **④コールドスタート**：プロセス起動時に一度だけ（常駐サーバーなので運用中は基本気にしない）
- **⑤状態の残存**：**残る**。1プロセスがずっと生きているので、グローバル変数やキャッシュがリクエストをまたいで共有される
- **⑥ファイルシステム**：あり
- **⑦並行性**：**イベントループ**。1スレッドだが、I/O 待ち（DB・ネットワーク）の間に他のリクエストを処理することで、**1プロセスで何千もの接続を同時にさばく**。CPU を使い切るには `cluster` / `worker_threads` / PM2 で複数プロセスを並べる
- **⑧どこで**：自前PC / EC2 / Fargate / Cloud Run などのコンテナ内

> 🎛️ **比喩**：php-fpm が「レジを何台も並べる」なら、Node は「**超高速で動く1人のレジ係**」。1人だが、客が財布を探している（I/O待ち）間に次の客の会計を進める、を高速で切り替えるので、結果的に大勢を同時にさばける。ただしその1人が**重い暗算（CPU処理）で固まると、列全体が止まる**（＝イベントループのブロッキング）。

**php-fpm との決定的な違い2点：**

1. **状態が残る**：Node はメモリ上の変数がリクエストをまたいで生き続けます。これは便利（接続プールやキャッシュを保持できる）な反面、**ユーザーAの情報がうっかりグローバルに残ってユーザーBに漏れる**といった事故の温床にもなります。PHP の「毎回まっさら」とは設計の前提が逆です。
2. **1プロセスで同時並行**：php-fpm は「同時数＝ワーカー数」ですが、Node は1プロセスで多数を同時に扱えます。そのぶん**重い同期処理（CPUバウンド）でイベントループを止めない**設計が必須です。

**コードのライフサイクル（Node 常駐サーバー）**

- 📥 **メモリ展開**：プロセス**起動時に `require`/`import` で全モジュールを読み込み・解析**し、コードをまるごとメモリに常駐させる（＝**最初から高いベースライン**）。以降リクエストで読み直さない。**読み込み元は、イメージを解凍してディスク（Fargateならエフェメラルストレージ）に展開したファイル**（詳細 → ③-3）
- ⚡ **実行**：リクエストごとにハンドラ（ルート処理）が走り、リクエスト用のオブジェクト/バッファを**ヒープに確保**。使い終わった分は V8 の GC が後でまとめて回収する
- 📊 **メモリプロファイル**：**コード部分のベースラインは最初から高く一定**。ただし**データ部分は負荷で増減**し、GC のたびに上下する（鋸歯状）。「処理中も非処理中も全く同じ」ではなく「**ベースが高い ＋ データが乗り降りする**」が正確

### (3) AWS Lambda（サーバーレス・関数）

「サーバーを立てっぱなしにする」のをやめ、**リクエスト（イベント）が来たときだけ動かす**モデルです。

- **①実行の単位**：**Firecracker という micro-VM**（極小の軽量仮想マシン）。1つの「実行環境（execution environment）」＝1つの micro-VM
- **②常駐**：あなたの視点では**していない**。AWS が必要なときに環境を起こし、不要になれば捨てる
- **③コードのロード**：環境が新規作成されるとき（＝コールドスタート時）に、デプロイパッケージを取得 → ランタイム起動 → **ハンドラ外のコード（初期化処理）を実行** → メモリに載る
- **④コールドスタート**：**ある。これが Lambda 最大の特徴**。暖まった環境が無いと、micro-VM 作成＋ランタイム起動＋コード初期化の時間（数十ms〜数秒）がレイテンシに乗る
- **⑤状態の残存**：**「同じ暖かい環境が再利用される間」は残る**。ハンドラの外で定義した変数・DB接続は次の呼び出しでも生きている（＝**実行コンテキストの再利用**）。ただし環境はいつ捨てられるか分からないので、**当てにはできない**
- **⑥ファイルシステム**：デプロイパッケージは**読み取り専用**。書けるのは `/tmp` のみ（一時的・揮発。環境が消えれば消える）
- **⑦並行性**：**1つの micro-VM は同時に1リクエストだけ**処理する。10件同時なら AWS が micro-VM を10個起動する（＝水平にスケール）。だから「同時実行数」という概念が中心になる
- **⑧どこで**：AWS 管理のインフラ（リージョン内）。サーバーの存在は見えない

> 🚕 **比喩**：php-fpm/Node が「店を開けて店員を待機させておく」なら、Lambda は「**注文が入った瞬間に、専用の調理ブースを1つ組み立てる**」。初回は組み立てに時間がかかる（コールドスタート）。一度組んだブースはしばらく次の注文にも使い回す（ウォームスタート＝実行コンテキスト再利用）。客が来ない時間が続くとブースは解体される。

**重要な実践ポイント**：DB接続のような重い初期化は**ハンドラの外**に書きます。そうすると暖かい環境が再利用される間は接続が生き続け、毎回の呼び出しで接続し直さずに済みます（コールドスタート時のみ接続）。これが「実行コンテキストの再利用」を活かす定石です。

**コードのライフサイクル（Lambda）**

- 📥 **メモリ展開**：コールドスタート時に、**ハンドラの中も外もコード一式を micro-VM のメモリに展開**する（SSD に置いたまま実行はされない）。**ハンドラ外のコードはこの Init で1回だけ実行**され、その結果（DB接続など）が変数としてメモリに残る。コードの実体は**デプロイパッケージ/イメージを micro-VM のストレージへ展開したもの**で、そこからメモリへ（書き込み可なのは `/tmp` のみ・エフェメラル）（詳細 → ③-3）
- ⚡ **実行**：リクエスト（Invoke）のたびに**ハンドラ関数だけ**が走る。ハンドラ外は再実行されない（暖かい環境を再利用する間）。＝**コードの置き場所ではなく「実行回数」が外と中で違う**
- 📊 **メモリプロファイル**：1環境＝1リクエストずつ処理。割り当てメモリ（128M〜10G）が上限。アイドル中の暖かい環境もメモリは保持する（ただし課金は実行時間ベース）

### (4) Cloudflare Workers（エッジ・isolate）

ここが一番「常識がひっくり返る」モデルです。**Workers はコンテナでも VM でもありません。**

- **①実行の単位**：**V8 isolate**。1つの OS プロセス（V8 ランタイム）の中に、**多数の isolate（メモリ的に隔離された軽量な箱）を同居**させる。コンテナや VM のように OS を起こさない
- **②常駐**：isolate 自体は必要に応じて作られ、使われなければ追い出される（evict）。プロセス（ランタイム）は常駐
- **③コードのロード**：isolate にスクリプトをロード／コンパイルして実行。VM やコンテナの起動が無いぶん極めて軽い
- **④コールドスタート**：**ほぼ 0**。VM/コンテナの起動が無く、isolate 生成はマイクロ秒〜ミリ秒オーダー。Cloudflare は TLS ハンドシェイク中に裏で準備してコールドスタートを隠すことすらある
- **⑤状態の残存**：**当てにできない**。isolate はいつでも捨てられる。永続したいデータは **Durable Objects / KV / D1 / R2** といった外部サービスに置く
- **⑥ファイルシステム**：**無い**。ディスクという概念がそもそも無い
- **⑦並行性**：isolate ごとにイベントループ（Node 的）。Cloudflare が多数の isolate を多数のリクエストに割り当てて並行をさばく
- **⑧どこで**：**エッジ**。世界中の数百拠点に同じコードを置き、**ユーザーに地理的に近い拠点**で実行する

> 📦 **比喩**：Lambda が「注文ごとに調理ブースを組み立てる」なら、Workers は「**1つの巨大なキッチンの中に、料理人ごとに仕切り板（isolate）を一瞬で立てる**」。ブース（VM）を建てないので待ち時間がほぼ無い。しかも**世界中の街角に同じキッチンがある**（エッジ）ので、客の家のすぐ近くで作れる。ただし仕切り板の中には**冷蔵庫（ディスク）も保管棚（永続メモリ）も無い**ので、材料は毎回外の倉庫（KV/R2/D1）から取る。

**なぜ isolate だとコールドスタートがほぼ 0 なのか**：コンテナや micro-VM は「OS（やその一部）を起動する」コストがかかります。isolate は OS を起動せず、すでに走っている V8 ランタイムの中に**メモリ空間を区切るだけ**なので、起動コストが桁違いに小さいのです。その代償が「ファイルシステム無し・Node API がそのままでは使えない・メモリやCPU時間の制約が厳しい」といった制限です（具体的な上限値はプランや時期で変わるため、使うときに公式ドキュメントで要確認）。

**コードのライフサイクル（Workers）**

- 📥 **メモリ展開**：スクリプトを **isolate にロード/コンパイルしてメモリ展開**（VM/コンテナの起動なし）。**ファイルシステムが無いので「イメージを解凍してディスクに展開→そこから読む」段階自体が無く**、コードはエッジのランタイムが配布・保持する（コンテナ型との対比は → ③-3）
- ⚡ **実行**：リクエストごとに isolate 内でハンドラ（`fetch` イベント）が走る。isolate は使われないと追い出される（evict）
- 📊 **メモリプロファイル**：isolate あたりのメモリ上限は小さめ（128M 程度・要確認）。多数の isolate が1プロセスに同居。**アイドル中の isolate はほぼコストにならない**（課金はリクエスト数＋CPU時間）

| --- | --- | --- | --- | --- |
| ①実行の単位 | プロセス（ワーカー複数） | 単一プロセス | Firecracker micro-VM | V8 isolate（VMでもコンテナでもない） |
| ②常駐 | する | する | しない（AWSが起こす/捨てる） | isolateは随時生成/破棄、ランタイムは常駐 |
| ③コードのロード | リクエスト毎＋OPcacheで再利用 | 起動時に一括ロード→常駐 | コールド時にロード＋初期化 | isolateにロード/コンパイル（超軽量） |
| ④コールドスタート | 実質なし | 起動時のみ | **ある（数十ms〜数秒）** | **ほぼ0** |
| ⑤状態の残存 | 残らない（毎回まっさら） | **残る**（事故にも注意） | 暖かい環境の間だけ残る（当てにしない） | 当てにできない（外部に保存） |
| ⑥ファイルシステム | あり | あり | 読取専用＋`/tmp`のみ（揮発） | **無し** |
| ⑦並行性 | ワーカー数＝同時数 | イベントループで1プロセス多重 | 1環境=1同時、足りなければ環境を増やす | 多数のisolateで多重 |

| ⑨メモリ増減（アイドル↔負荷） | ベース低〜中＋負荷でデータ増 | **ベース高（コード常駐）**＋負荷でデータ増 | 環境数で増、各環境に割当上限 | isolate単位で小、アイドルはほぼ0 |

**読み解きのコツ**：上から下へ行くほど「**プロセスを立てっぱなしにする**」発想から「**必要なときに必要なぶんだけ動かす**」発想へ移ります。その代わりに、状態の永続性やファイルシステムといった「立てっぱなしだから当然に使えていたもの」を失っていく、というトレードオフが見えます。

## ③-2 ECS でのメモリ挙動：Laravel（実）vs Node（仮）

ここは「ECS で動かしたとき、リクエストの有無でメモリ使用率はどう動くのか」という具体的な疑問への回答です。前提として、**ECS（Fargate）はタスク定義で固定のメモリ量を割り当てます**。その**固定枠の中で、php-fpm と Node では「枠の埋まり方」が対照的**になります。鍵は前述の **「コードのメモリ（基本一定）」と「データのメモリ（負荷で増減）」** の切り分けです。

### ECS Laravel（php-fpm）← 本プロジェクトの実態

- **タスク起動時**：master ＋ **10ワーカーが固定で立ち上がる**（`pm = static`）。この時点のベースライン＝「プロセス群 ＋ 徐々に埋まる OPcache 共有メモリ」
- **リクエスト処理時**：各ワーカーがリクエストごとのデータを `memory_limit = 256M` 以内で確保。**同時に捌くリクエストが多いほどデータ部分が膨らみ、メモリ使用率が上がる**
- **アイドル時**：shared-nothing で各リクエスト終了時にデータを解放 → ベースライン付近へ戻る
- **結論**：「リクエスト処理時にメモリ使用率が上がる」は **あなたの言うとおり ⭕**。ただし `pm = static` なので**増えるのは「ワーカー（プロセス）数」ではなく「各ワーカーが握るデータ量」**。さらに `pm.max_requests = 1000` で1000件ごとにワーカーを再起動し、リークでメモリが右肩上がりになるのを防いでいる
- **注意点**：`pm.max_children = 10` × `memory_limit = 256M` ＝ 理論上**最大2.5GB**（`docs/local-dev/php_ini_review.md` が指摘）。Fargate のタスクメモリがこれを下回ると、高負荷時に **OOM（メモリ不足でタスク強制終了）** のリスク

### ECS Node（仮：もし常駐 Node をここで動かしたら）

> ※ 本プロジェクトの React は本番では静的配信なので、これは「もし ECS に常駐 Node サーバーを置いたら」という仮の比較です。

- **タスク起動時**：全モジュールをロード・解析 → **最初から高いベースライン**
- **リクエスト処理時**：ここがあなたの仮説の**補正ポイント**。「処理中も非処理中もメモリは変わらない」は厳密には少し違う。**コード部分は確かに一定**だが、**リクエストごとのデータ（オブジェクト/バッファ）はヒープに積まれる**ので、負荷でメモリは増え、GC で戻る（鋸歯状）
- **正確な言い方**：「**コード由来のベースラインが高く一定**」＝ ⭕／「**だからメモリが全く変動しない**」＝ △（データ部分は変動する）
- **php-fpm との対比**：php-fpm はベースが低めで、リクエスト量に比例した上下が目立つ。Node はベースが高く、その上の変動は GC 任せでなだらか

### 一言でまとめると

| 見る対象 | php-fpm（ECS Laravel・実） | Node（ECS・仮） |
| --- | --- | --- |
| **コードのメモリ** | 起動時にワーカー常駐＋OPcacheに徐々に。ベースは中くらい | **起動時に全展開でベースが高い**。一定 |
| **データのメモリ** | リクエストごとに確保→解放。負荷で増減が目立つ | リクエストごとにヒープへ。負荷で増減（GCで上下） |

あなたの直感のうち **正しい部分は「Node はコードのベースラインが高く一定」**、**補正すべき部分は「データは依然として負荷で増減する」** です。どちらの方式も「データのメモリ」は負荷で動く、というのが共通点です。

## ③-3 イメージはどこに解凍され、どこからメモリに載るか（Fargate vs EC2）

「コードは結局どのディスクから来てメモリに載るのか」を、コンテナの仕組みから整理します。大原則（姉妹編）は **CPU はメモリしか実行できない**。なのでコードは必ず「**どこかのディスク → メモリ**」という経路をたどります。その「どこかのディスク」が、起動タイプで変わります。

### まずコンテナ共通の仕組み（イメージ → ディスク → メモリ）

1. **イメージはレジストリ（ECR）に、圧縮された層（レイヤー）の積み重ねとして置かれている**（gzip で固めた tar）
2. コンテナ起動時、ランタイムがその層を**ダウンロードして解凍・展開**し、ホストのディスクに置く
3. 読み取り専用の層に薄い書き込み可能層を重ね、**overlayfs（重ね合わせファイルシステム）**で1つの普通のファイルツリーに見せる ← これがコンテナ内のコードの正体
4. プロセス（php-fpm / Node）がコードを使うとき、この**ディスク上のファイルをメモリ（OSのページキャッシュ）に読み込み**、CPU が実行する

つまり各 📥 行で「メモリに展開」と書いたのは、正確には **「解凍してディスクに展開したコードを、実行時にメモリへ読み込む」**。**「ディスクに展開」と「メモリに読み込む」は別の段階**です。

### Fargate の場合（本プロジェクトの本番）

- 上記の「ホストのディスク」＝ **Fargate 管理の、タスクごとに隔離されたエフェメラル（一時）ストレージ**（PV1.4+ で 20GiB、AES-256 暗号化。出典：[ECS Fargate security best practices](https://docs.aws.amazon.com/AmazonECS/latest/bestpracticesguide/security-fargate.html)）。**タスクが消えれば一緒に消える**
- ⚠️ **「共有」ではない**：物理ハードは AWS が多数の顧客で共用していても、**タスクに見えるストレージは隔離**されている。だから「共有SSD」より「**隔離されたエフェメラルストレージ**」が正確
- あなたは「サーバー（ホスト）を管理しない」が、その裏で AWS がこのストレージを用意し、そこにイメージを解凍して置き、そこからメモリへ読み込んでいる

### EC2 起動タイプの場合（このプロジェクトでは未使用＝仮の話）

- 「ホストのディスク」＝ **あなたが立てた EC2 インスタンスのストレージ**。通常は **EBS（Elastic Block Store）ルートボリューム**（イメージ層は `/var/lib/docker` 等に展開）。インスタンスタイプ次第ではインスタンスストアのことも
- あなたの「**EC2 なら EBS**」は ⭕。永続データ用の Docker volume が **EC2 でのみ使える**のも、ディスクが EC2 インスタンスに紐づくため（出典：[Docker volumes](https://docs.aws.amazon.com/AmazonECS/latest/bestpracticesguide/storage-dockervolumes.html)）
- Fargate との違いは「**そのディスクを誰が用意・管理するか**」だけ。Fargate は AWS、EC2 はあなた（EBS のサイズ・暗号化・寿命を自分で管理）。コードが「ディスク → メモリ」で動く原理は同じ

### Workers は別世界（対比）

- Workers は**コンテナでも VM でもなく、ファイルシステムが無い**。だから「イメージを解凍してディスクに展開」という段階が**そもそも存在しない**
- コードはエッジのランタイムがスクリプトとして配布・保持し、isolate へ直接ロードする。**ディスクを経由しない**
- ローカルにファイルを読み書きする・ディスクにキャッシュする、といった前提が使えないのはこのため

### まとめ表

| | コードの置き場所（解凍後） | 誰が用意・管理 | 寿命 |
| --- | --- | --- | --- |
| ECS Fargate | タスク隔離のエフェメラルストレージ | AWS(Fargate) | タスク終了で消える |
| ECS EC2（仮） | EC2 の EBS ルートボリューム等 | あなた | インスタンス/ボリューム次第 |
| Lambda | micro-VM のストレージ（＋ `/tmp`） | AWS | 環境破棄で消える |
| Workers | ディスクなし（ランタイムが保持） | Cloudflare | — |

## ④ 落とし穴・関連トピック

- **「サーバーレス＝サーバーが無い」ではない**：Lambda も裏で micro-VM が動いている。Workers も V8 ランタイムのプロセスが走っている。「**自分で管理しない**」だけです。
- **Node の状態共有は諸刃の剣**：php-fpm から来た人が「リクエストごとにまっさら」だと思い込むと、グローバル変数の汚染で情報漏洩やバグを起こします。逆に Lambda/Workers に来た人が「状態が残る」前提でコードを書くと、環境が捨てられた瞬間に壊れます。
- **コールドスタート対策**：Lambda では重い初期化をハンドラ外に置く・Provisioned Concurrency で暖めておく、などの手がある。Workers はそもそもコールドスタートがほぼ無いのが売り。
- **このプロジェクトとの接続**：本プロジェクトは「**常駐プロセス型**」（php-fpm を Fargate コンテナで常駐／Cloud Run も常駐コンテナ）を選んでいます。Lambda/Workers 型ではありません。なぜ常駐コンテナを選んだのか、という観点で `docs/aws-infra/` や `docs/adr/` を読むと、この比較が「自分たちの選択」として腑に落ちます。
- **次に学ぶとよい関連概念**：イベントループとブロッキング（Node）、Firecracker と実行コンテキスト再利用（Lambda）、V8 isolate とエッジコンピューティング（Workers）、そして「ステートフル vs ステートレス」という設計の軸。

## 用語集

- **shared-nothing** — リクエストごとにメモリを共有せず、毎回まっさらから始める方式（php-fpm/PHP）。事故が起きにくい
- **イベントループ** — 1スレッドで、I/O待ちの隙間に別の処理を回すことで多数の同時処理をさばく仕組み（Node/Workers）
- **ブロッキング** — イベントループ上で重い同期処理をして、他のリクエスト処理を止めてしまうこと
- **JIT（Just-In-Time コンパイル）** — 実行中に頻出コードを機械語へ変換して高速化する仕組み（V8 など）
- **micro-VM / Firecracker** — Lambda が使う極小の軽量仮想マシン。1実行環境＝1 micro-VM
- **コールドスタート** — 実行環境を新規に用意する時間がレイテンシに乗ること。Lambda で顕著、Workers ではほぼ無い
- **実行コンテキストの再利用（warm start）** — Lambda で暖まった環境が次の呼び出しにも使い回され、初期化を省ける状態
- **V8 isolate** — 1プロセス内に多数同居できる、メモリ隔離された軽量な実行コンテキスト。コンテナや VM ではない
- **エッジ** — 世界中の多数拠点。ユーザーに地理的に近い場所でコードを実行する（Workers）
- **ステートレス / ステートフル** — リクエストをまたいで状態を持たない／持つ、という設計上の性質
- **コードのメモリ / データのメモリ** — 前者はプログラム本体（展開後は基本一定）、後者はリクエストごとに確保されるオブジェクト等（負荷で増減）。メモリ挙動はこの2つを分けて考える
- **ヒープ** — プログラムが実行中に動的に確保するメモリ領域。リクエストごとのデータはここに積まれる
- **ガベージコレクション（GC）** — 使われなくなったヒープ上のデータを自動回収する仕組み（V8 など）。Node のメモリが鋸歯状に上下する原因
- **pm = static** — php-fpm のプロセス管理方式。ワーカー数を起動時に固定する。Fargate の固定メモリと相性がよく OOM を避けやすい（`environment/ecr/zz-custom.conf`）
- **OOM（Out Of Memory）** — メモリ上限を超えてプロセス/タスクが強制終了されること
- **イメージレイヤー** — コンテナイメージを構成する読み取り専用の層。レジストリには圧縮された tar として保存され、起動時に解凍・展開される
- **overlayfs（重ね合わせFS）** — 読み取り専用のイメージ層＋薄い書き込み可能層を重ねて1つのファイルツリーに見せる仕組み。コンテナ内のファイルシステムの正体
- **エフェメラルストレージ** — タスク/環境の寿命と一緒に消える一時ディスク。Fargate はタスクごとに隔離して提供（PV1.4+ で 20GiB・暗号化）
- **EBS（Elastic Block Store）** — EC2 にアタッチするブロックストレージ。ECS on EC2 ではイメージ層もここ（ルートボリューム）に展開されるのが通常
- **ページキャッシュ** — OS が一度読んだディスク上のファイルをメモリに保持する仕組み。ディスク → メモリの読み込みを速くする
