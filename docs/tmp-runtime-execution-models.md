# 実行モデル比較：php-fpm / Node常駐サーバー / Lambda / Cloudflare Workers

## ① 結論（先に答え）

「コードは SSD に保管され、実行はメモリで起きる」という大原則（姉妹編で説明）は**4つすべてで共通**です。違うのは **「リクエストをどうさばくか」「プロセスがいつ生まれて、いつ死ぬか」** です。ここが4者を分ける本質です。

ざっくり一言でいうと：

- **php-fpm**：リクエストごとにワーカーが1件を担当。**毎回まっさらな状態**から始める（共有なし）。
- **Node常駐サーバー**：**たった1つのプロセス**が、イベントループで**大量のリクエストを同時並行**にさばく。状態はメモリに残り続ける。
- **AWS Lambda**：リクエスト（イベント）が来た**瞬間に環境（micro-VM）が起動**。使い終わるとしばらく再利用され、やがて捨てられる。**コールドスタート**がある。
- **Cloudflare Workers**：そもそも**コンテナでも VM でもない**。**V8 isolate** という超軽量な箱で動き、**コールドスタートがほぼ 0**。代わりにファイルシステムが無く制約も多い。

## ② それぞれの仕組み（8つの軸で見る）

以下、8つの軸で1つずつ見ていきます。

> 軸：①実行の単位 / ②常駐しているか / ③コードはいつメモリに載るか / ④コールドスタート / ⑤リクエスト間で状態が残るか / ⑥ファイルシステム / ⑦並行リクエストのさばき方 / ⑧どこで動くか

### (1) php-fpm（おさらい＋並行性の補足）

- **①実行の単位**：OS プロセス（マスター＋複数ワーカー）
- **②常駐**：する。起動時からワーカーがメモリに居座る
- **③コードのロード**：リクエストごとに必要ファイルを遅延読込 →（OPcache 有効なら）2回目以降はメモリの opcode を再利用
- **④コールドスタート**：実質意識しない（常駐しているので）
- **⑤状態の残存**：**残らない（shared-nothing）**。各リクエストはまっさらなメモリから始まり、終了で破棄
- **⑥ファイルシステム**：あり（コンテナ／ホストのディスク）
- **⑦並行性**：**プロセス（ワーカー）を複数並べる**。1ワーカー＝同時に1リクエスト。10件同時なら最低10ワーカー必要
- **⑧どこで**：自前PC / EC2 / Fargate などのコンテナ内

> 🏪 **比喩**：レジ（ワーカー）を何台も並べた店。1台のレジは一度に1人しか対応できない。混んだらレジを増やす。各客の対応は独立していて、前の客の情報は次に持ち越さない。

PHP が「shared-nothing（毎回まっさら）」なのは弱点に見えて、**状態の取り違えが起きにくい**という安全性の利点でもあります。

### (2) Node.js 常駐サーバー（Express / Next.js SSR など）

ここが php-fpm と最も鋭く対照的です。

- **①実行の単位**：**1つのプロセス**（基本シングルスレッド）
- **②常駐**：する。`node server.js` で起動したプロセスがずっと生きている
- **③コードのロード**：**起動時に `require`/`import` で必要モジュールを一括で読み込み・解析**し、メモリに常駐させる。以降リクエストのたびに読み直さない（V8 が頻出コードを JIT で機械語化して更に高速化）
- **④コールドスタート**：プロセス起動時に一度だけ（常駐サーバーなので運用中は基本気にしない）
- **⑤状態の残存**：**残る**。1プロセスがずっと生きているので、グローバル変数やキャッシュがリクエストをまたいで共有される
- **⑥ファイルシステム**：あり
- **⑦並行性**：**イベントループ**。1スレッドだが、I/O 待ち（DB・ネットワーク）の間に他のリクエストを処理することで、**1プロセスで何千もの接続を同時にさばく**。CPU を使い切るには `cluster` / `worker_threads` / PM2 で複数プロセスを並べる
- **⑧どこで**：自前PC / EC2 / Fargate / Cloud Run などのコンテナ内

> 🎛️ **比喩**：php-fpm が「レジを何台も並べる」なら、Node は「**超高速で動く1人のレジ係**」。1人だが、客が財布を探している（I/O待ち）間に次の客の会計を進める、を高速で切り替えるので、結果的に大勢を同時にさばける。ただしその1人が**重い暗算（CPU処理）で固まると、列全体が止まる**（＝イベントループのブロッキング）。

**php-fpm との決定的な違い2点：**

1. **状態が残る**：Node はメモリ上の変数がリクエストをまたいで生き続けます。これは便利（接続プールやキャッシュを保持できる）な反面、**ユーザーAの情報がうっかりグローバルに残ってユーザーBに漏れる**といった事故の温床にもなります。PHP の「毎回まっさら」とは設計の前提が逆です。
2. **1プロセスで同時並行**：php-fpm は「同時数＝ワーカー数」ですが、Node は1プロセスで多数を同時に扱えます。そのぶん**重い同期処理（CPUバウンド）でイベントループを止めない**設計が必須です。

### (3) AWS Lambda（サーバーレス・関数）

「サーバーを立てっぱなしにする」のをやめ、**リクエスト（イベント）が来たときだけ動かす**モデルです。

- **①実行の単位**：**Firecracker という micro-VM**（極小の軽量仮想マシン）。1つの「実行環境（execution environment）」＝1つの micro-VM
- **②常駐**：あなたの視点では**していない**。AWS が必要なときに環境を起こし、不要になれば捨てる
- **③コードのロード**：環境が新規作成されるとき（＝コールドスタート時）に、デプロイパッケージを取得 → ランタイム起動 → **ハンドラ外のコード（初期化処理）を実行** → メモリに載る
- **④コールドスタート**：**ある。これが Lambda 最大の特徴**。暖まった環境が無いと、micro-VM 作成＋ランタイム起動＋コード初期化の時間（数十ms〜数秒）がレイテンシに乗る
- **⑤状態の残存**：**「同じ暖かい環境が再利用される間」は残る**。ハンドラの外で定義した変数・DB接続は次の呼び出しでも生きている（＝**実行コンテキストの再利用**）。ただし環境はいつ捨てられるか分からないので、**当てにはできない**
- **⑥ファイルシステム**：デプロイパッケージは**読み取り専用**。書けるのは `/tmp` のみ（一時的・揮発。環境が消えれば消える）
- **⑦並行性**：**1つの micro-VM は同時に1リクエストだけ**処理する。10件同時なら AWS が micro-VM を10個起動する（＝水平にスケール）。だから「同時実行数」という概念が中心になる
- **⑧どこで**：AWS 管理のインフラ（リージョン内）。サーバーの存在は見えない

> 🚕 **比喩**：php-fpm/Node が「店を開けて店員を待機させておく」なら、Lambda は「**注文が入った瞬間に、専用の調理ブースを1つ組み立てる**」。初回は組み立てに時間がかかる（コールドスタート）。一度組んだブースはしばらく次の注文にも使い回す（ウォームスタート＝実行コンテキスト再利用）。客が来ない時間が続くとブースは解体される。

**重要な実践ポイント**：DB接続のような重い初期化は**ハンドラの外**に書きます。そうすると暖かい環境が再利用される間は接続が生き続け、毎回の呼び出しで接続し直さずに済みます（コールドスタート時のみ接続）。これが「実行コンテキストの再利用」を活かす定石です。

### (4) Cloudflare Workers（エッジ・isolate）

ここが一番「常識がひっくり返る」モデルです。**Workers はコンテナでも VM でもありません。**

- **①実行の単位**：**V8 isolate**。1つの OS プロセス（V8 ランタイム）の中に、**多数の isolate（メモリ的に隔離された軽量な箱）を同居**させる。コンテナや VM のように OS を起こさない
- **②常駐**：isolate 自体は必要に応じて作られ、使われなければ追い出される（evict）。プロセス（ランタイム）は常駐
- **③コードのロード**：isolate にスクリプトをロード／コンパイルして実行。VM やコンテナの起動が無いぶん極めて軽い
- **④コールドスタート**：**ほぼ 0**。VM/コンテナの起動が無く、isolate 生成はマイクロ秒〜ミリ秒オーダー。Cloudflare は TLS ハンドシェイク中に裏で準備してコールドスタートを隠すことすらある
- **⑤状態の残存**：**当てにできない**。isolate はいつでも捨てられる。永続したいデータは **Durable Objects / KV / D1 / R2** といった外部サービスに置く
- **⑥ファイルシステム**：**無い**。ディスクという概念がそもそも無い
- **⑦並行性**：isolate ごとにイベントループ（Node 的）。Cloudflare が多数の isolate を多数のリクエストに割り当てて並行をさばく
- **⑧どこで**：**エッジ**。世界中の数百拠点に同じコードを置き、**ユーザーに地理的に近い拠点**で実行する

> 📦 **比喩**：Lambda が「注文ごとに調理ブースを組み立てる」なら、Workers は「**1つの巨大なキッチンの中に、料理人ごとに仕切り板（isolate）を一瞬で立てる**」。ブース（VM）を建てないので待ち時間がほぼ無い。しかも**世界中の街角に同じキッチンがある**（エッジ）ので、客の家のすぐ近くで作れる。ただし仕切り板の中には**冷蔵庫（ディスク）も保管棚（永続メモリ）も無い**ので、材料は毎回外の倉庫（KV/R2/D1）から取る。

**なぜ isolate だとコールドスタートがほぼ 0 なのか**：コンテナや micro-VM は「OS（やその一部）を起動する」コストがかかります。isolate は OS を起動せず、すでに走っている V8 ランタイムの中に**メモリ空間を区切るだけ**なので、起動コストが桁違いに小さいのです。その代償が「ファイルシステム無し・Node API がそのままでは使えない・メモリやCPU時間の制約が厳しい」といった制限です（具体的な上限値はプランや時期で変わるため、使うときに公式ドキュメントで要確認）。

## ③ 8軸の比較表（まとめ）

| 軸 | php-fpm | Node 常駐サーバー | AWS Lambda | Cloudflare Workers |
| --- | --- | --- | --- | --- |
| ①実行の単位 | プロセス（ワーカー複数） | 単一プロセス | Firecracker micro-VM | V8 isolate（VMでもコンテナでもない） |
| ②常駐 | する | する | しない（AWSが起こす/捨てる） | isolateは随時生成/破棄、ランタイムは常駐 |
| ③コードのロード | リクエスト毎＋OPcacheで再利用 | 起動時に一括ロード→常駐 | コールド時にロード＋初期化 | isolateにロード/コンパイル（超軽量） |
| ④コールドスタート | 実質なし | 起動時のみ | **ある（数十ms〜数秒）** | **ほぼ0** |
| ⑤状態の残存 | 残らない（毎回まっさら） | **残る**（事故にも注意） | 暖かい環境の間だけ残る（当てにしない） | 当てにできない（外部に保存） |
| ⑥ファイルシステム | あり | あり | 読取専用＋`/tmp`のみ（揮発） | **無し** |
| ⑦並行性 | ワーカー数＝同時数 | イベントループで1プロセス多重 | 1環境=1同時、足りなければ環境を増やす | 多数のisolateで多重 |
| ⑧どこで | 自前/EC2/Fargate等のコンテナ | 自前/EC2/Fargate/CloudRun等 | AWS管理インフラ（リージョン） | **エッジ（世界中の拠点）** |

**読み解きのコツ**：上から下へ行くほど「**プロセスを立てっぱなしにする**」発想から「**必要なときに必要なぶんだけ動かす**」発想へ移ります。その代わりに、状態の永続性やファイルシステムといった「立てっぱなしだから当然に使えていたもの」を失っていく、というトレードオフが見えます。

## ④ 落とし穴・関連トピック

- **「サーバーレス＝サーバーが無い」ではない**：Lambda も裏で micro-VM が動いている。Workers も V8 ランタイムのプロセスが走っている。「**自分で管理しない**」だけです。
- **Node の状態共有は諸刃の剣**：php-fpm から来た人が「リクエストごとにまっさら」だと思い込むと、グローバル変数の汚染で情報漏洩やバグを起こします。逆に Lambda/Workers に来た人が「状態が残る」前提でコードを書くと、環境が捨てられた瞬間に壊れます。
- **コールドスタート対策**：Lambda では重い初期化をハンドラ外に置く・Provisioned Concurrency で暖めておく、などの手がある。Workers はそもそもコールドスタートがほぼ無いのが売り。
- **このプロジェクトとの接続**：本プロジェクトは「**常駐プロセス型**」（php-fpm を Fargate コンテナで常駐／Cloud Run も常駐コンテナ）を選んでいます。Lambda/Workers 型ではありません。なぜ常駐コンテナを選んだのか、という観点で `docs/aws-infra/` や `docs/adr/` を読むと、この比較が「自分たちの選択」として腑に落ちます。
- **次に学ぶとよい関連概念**：イベントループとブロッキング（Node）、Firecracker と実行コンテキスト再利用（Lambda）、V8 isolate とエッジコンピューティング（Workers）、そして「ステートフル vs ステートレス」という設計の軸。

## 用語集

- **shared-nothing** — リクエストごとにメモリを共有せず、毎回まっさらから始める方式（php-fpm/PHP）。事故が起きにくい
- **イベントループ** — 1スレッドで、I/O待ちの隙間に別の処理を回すことで多数の同時処理をさばく仕組み（Node/Workers）
- **ブロッキング** — イベントループ上で重い同期処理をして、他のリクエスト処理を止めてしまうこと
- **JIT（Just-In-Time コンパイル）** — 実行中に頻出コードを機械語へ変換して高速化する仕組み（V8 など）
- **micro-VM / Firecracker** — Lambda が使う極小の軽量仮想マシン。1実行環境＝1 micro-VM
- **コールドスタート** — 実行環境を新規に用意する時間がレイテンシに乗ること。Lambda で顕著、Workers ではほぼ無い
- **実行コンテキストの再利用（warm start）** — Lambda で暖まった環境が次の呼び出しにも使い回され、初期化を省ける状態
- **V8 isolate** — 1プロセス内に多数同居できる、メモリ隔離された軽量な実行コンテキスト。コンテナや VM ではない
- **エッジ** — 世界中の多数拠点。ユーザーに地理的に近い場所でコードを実行する（Workers）
- **ステートレス / ステートフル** — リクエストをまたいで状態を持たない／持つ、という設計上の性質
